# AGENTS.md

## Проект
- Frontend: `Next.js 16` (`App Router`), `React 19`, `TypeScript`, `Tailwind CSS 4`
- Backend API: `FastAPI`
- Локальная база: `SQLite` (`stock_sync.db`)
- Интеграции и импорт: `pandas`, `openpyxl`, локальная интеграция с `1С`
- Запуск и обслуживание: `PowerShell` / `bat`

## Базовые команды

### Полный запуск приложения
- `start_all.bat`
- остановка: `stop_all.bat`

### Backend
- `.\.venv\Scripts\python.exe -m uvicorn stock_sync_api:app --host 0.0.0.0 --port 8000`
- служебный скрипт: `.\scripts\run_backend_service.ps1`

### Frontend
- `cd sm-techno-web`
- dev: `npm run dev -- --hostname 127.0.0.1 --port 3000`
- build: `npm run build`
- start: `npm run start -- --hostname 0.0.0.0 --port 3000`
- lint: `npm run lint`
- typecheck (ad hoc): `npx tsc --noEmit`

### Тесты
- Backend: `python -m pytest tests/auth -q --strict-markers`, затем `python -m pytest tests -q --strict-markers`.
- Frontend: `npm ci`, `npm run test:auth`, `npm run test:settings`, `npm run lint`, `npx tsc --noEmit --incremental false`, `npm run build`, `npm run test:auth:e2e`.
- Тесты запускаются в отдельной копии с временными БД/storage и синтетическим Fernet-ключом. Не передавать рабочие настройки 1С. E2E запускать только через npm script с allowlist окружения.

## Обязательные правила
- Не ломать существующую логику остатков, резервов, счетов, заказов, складов и импорта Excel.
- Не менять API-контракты, схему данных, миграции и интеграцию с 1С без отдельного подтвержденного плана.
- Для отображения, поиска, журналов, КП, договоров, спецификаций и имен файлов клиента использовать наименование для документов из 1С: `Наименование для документов` / `НаименованиеПолное` (`document_name` / `full_name`). Поле `Наименование в программе` / `Description` / `name` не должно подставляться в печатные формы и клиентские снапшоты, кроме аварийной совместимости со старыми пустыми данными.
- Для сложных задач сначала составлять план, затем работать этапами.
- Перед завершением запускать доступные проверки и кратко фиксировать, что именно было изменено и что было проверено.
- Если в рабочем дереве есть чужие или неожиданные изменения, не откатывать их автоматически.

## Ветки и интеграция

- Единственная постоянная линия разработки и интеграции — `main`; постоянную `develop` не создавать.
- Новые задачи: свежая `origin/main`, отдельная короткоживущая `codex/<задача>` и отдельный worktree/клон. Не переключать чужой dirty checkout, не прятать его автоматически через stash.
- Включение изменений только через PR в main и фактические обязательные проверки. После включения временная ветка удаляется с проверкой зависимостей и сохранением нужного архивного состояния.
- Архивный аннотированный тег `archive/<дата>/<ветка>` фиксирует явный SHA; это не стабильный релиз. Существующие теги не перезаписывать.
- Порядок: [release-workflow](docs/release-workflow.md), [deployment-source-of-truth](docs/deployment-source-of-truth.md), [frontend](docs/FRONTEND_WORKFLOW.md).
- `docs/superpowers/`, `sm-techno-web/docs/superpowers/`, `.superpowers/` — исторические планы/отчёты, не текущие инструкции. Читать только для конкретной исторической задачи.

## Деплой — отдельная операция

Слияние PR, публикация архивного тега и удаление ветки не являются разрешением на выпуск или деплой. Перед любой публикацией проверить автоматические внешние триггеры, согласовать целевой контур и точный SHA из main.

Sites и Vercel не используются и исключены из контуров публикации; Vercel Git deployments отключены в обеих конфигурациях. Не обращаться к ним как к целям деплоя и не блокировать merge/release из-за их прежнего статуса или зеркал.

Оставшийся серверный/локальный контур и фактический серверный SHA требуют проверки. Проверка 2026-10-06: VPS `91.227.68.176` отклонил вход с доступными SSH-ключами; не объявлять его подтверждённой целью и не считать текущий runtime установленным. Зависимости от `codex/vps-self-hosting` требуют сверки; ветку пока сохранять. VPS runbook [isolated-vps-test-deployment](docs/isolated-vps-test-deployment.md) — справочник для отдельного согласованного обслуживания.

Не изменять DNS, Caddy, чужие контейнеры/сети/тома, рабочую БД/storage и настройки 1С. Перед отдельным деплоем необходим проверенный согласованный backup; не подменять каталог data SQLite-файлом. Не выполнять фоновые обмены и записи в рабочую 1С из тестов.
