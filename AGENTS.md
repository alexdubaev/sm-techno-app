# AGENTS.md

## Проект
- Frontend: `Next.js 16` (`App Router`), `React 19`, `TypeScript`, `Tailwind CSS 4`
- Backend API: `FastAPI`
- Локальная база: `SQLite` (`stock_sync.db`)
- Интеграции и импорт: `pandas`, `openpyxl`, локальная интеграция с `1С`
- Запуск и обслуживание: `PowerShell` / `bat`

## Базовые команды

### Полный запуск приложения
- `start_all.bat`
- остановка: `stop_all.bat`

### Backend
- `.\.venv\Scripts\python.exe -m uvicorn stock_sync_api:app --host 0.0.0.0 --port 8000`
- служебный скрипт: `.\scripts\run_backend_service.ps1`

### Frontend
- `cd sm-techno-web`
- dev: `npm run dev -- --hostname 127.0.0.1 --port 3000`
- build: `npm run build`
- start: `npm run start -- --hostname 0.0.0.0 --port 3000`
- lint: `npm run lint`
- typecheck (ad hoc): `npx tsc --noEmit`

### Тесты
- Отдельная автоматическая test-команда сейчас не настроена.
- Минимальный smoke-check делается через `npm run build`, `npm run lint` и ручную проверку ключевых сценариев.

## Обязательные правила
- Не ломать существующую логику остатков, резервов, счетов, заказов, складов и импорта Excel.
- Не менять API-контракты, схему данных, миграции и интеграцию с 1С без отдельного подтвержденного плана.
- Для отображения, поиска, журналов, КП, договоров, спецификаций и имен файлов клиента использовать наименование для документов из 1С: `Наименование для документов` / `НаименованиеПолное` (`document_name` / `full_name`). Поле `Наименование в программе` / `Description` / `name` не должно подставляться в печатные формы и клиентские снапшоты, кроме аварийной совместимости со старыми пустыми данными.
- Для сложных задач сначала составлять план, затем работать этапами.
- Перед завершением запускать доступные проверки и кратко фиксировать, что именно было изменено и что было проверено.
- Если в рабочем дереве есть чужие или неожиданные изменения, не откатывать их автоматически.

## Ветки и интеграция

### Единственная рабочая линия
- Основная рабочая и интеграционная ветка проекта — `codex/vps-self-hosting`.
- Перед созданием новой задачи получить актуальную `origin/codex/vps-self-hosting` и создавать отдельную ветку `codex/<задача>` и worktree именно от неё.
- Не начинать новую работу напрямую от `main`, от старой feature-ветки или от устаревшего commit `codex/vps-self-hosting`.
- После проверок подтверждённые изменения feature-ветки вливаются в `codex/vps-self-hosting`, а не в `main`.
- `codex/vps-self-hosting` вливается в `main` только по явной команде пользователя. Агент не предлагает, не выполняет и не готовит это слияние самостоятельно.

### Закрытые ветки
- Все ветки, ответвлённые от `main` и не являющиеся `codex/vps-self-hosting` или её потомками, считаются закрытыми.
- В закрытых ветках и их worktree нельзя работать, читать исходники, запускать тесты, проверять сборку, делать commit, rebase, merge или иные изменения.
- Закрытые ветки не удалять без явного запроса пользователя. Для новой задачи всегда создавать чистую ветку от актуальной `origin/codex/vps-self-hosting`.

## Деплой на crm-cmteh.ru

Деплой — внешнее изменение. Выполнять его только по явной команде пользователя после того, как нужный commit уже есть в `codex/vps-self-hosting` и отправлен в GitHub.

### Контур и границы
- VPS-приложение находится в `/srv/sm-techno-test/app`; Compose-проект — `sm-techno-test`.
- Рабочая БД: `/srv/sm-techno-test/data/stock_sync.db`. `data` — каталог, его нельзя заменять SQLite-файлом.
- Backend доступен только на VPS loopback. Публичная проверка выполняется через `https://crm-cmteh.ru`.
- Не изменять DNS, Caddy, сети или контейнеры других проектов на VPS.

### Порядок деплоя
1. Запустить относящиеся к изменению проверки локально, commit и push нужного SHA в `codex/vps-self-hosting`.
2. На VPS выполнить backup перед обновлением, особенно перед миграцией данных:

   ```bash
   cd /srv/sm-techno-test/app
   python3 scripts/vps_backup.py --root /srv/sm-techno-test --backups-dir /srv/sm-techno-test/backups
   ```

3. Обновить `/srv/sm-techno-test/app` ровно файлами утверждённого commit. Не подменять каталог `data` или `storage`; способ доставки кода не выдумывать, если он не подтверждён пользователем или текущим серверным контуром.
4. Пересобрать и перезапустить только сервисы приложения:

   ```bash
   cd /srv/sm-techno-test/app
   docker compose -p sm-techno-test build backend frontend
   docker compose -p sm-techno-test up -d --force-recreate backend frontend
   docker compose -p sm-techno-test ps
   curl -fsS http://127.0.0.1:3000/api/health
   curl -fsS https://crm-cmteh.ru/api/health
   ```

5. Продолжать только если оба health-check вернули `ok` и оба контейнера healthy; затем вручную проверить пользовательский сценарий, который затрагивал релиз.
6. При неуспешном обновлении не выполнять опасные массовые команды. Сначала сохранить диагностику и согласовать с пользователем откат из созданного backup.
