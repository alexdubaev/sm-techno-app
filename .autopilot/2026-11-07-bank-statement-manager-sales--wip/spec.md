# Спецификация: банковские оплаты в существующих продажах менеджеров

## 1. Задача и границы

Администратор закрепляет клиентов за менеджерами по продажам, один раз загружает XLSX по организации, видит проверенные предложения и подтверждает готовые оплаты. Одна подтверждённая входящая банковская операция появляется ровно одной записью в существующей `manager_sales`, у менеджера, действовавшего на дату поступления. Те же операции доступны в карточке клиента с учётом прав. Проблемы сохраняются и исправляются без повторной загрузки. Это реализация функции, включая сохранение, API, UI, проверки и PR.

В продажи попадает **полная сумма поступления с НДС**. НДС не вычитается, не вычисляется из назначения и не является обязательным условием проведения. Импорт не меняет функцию зарплаты, планы, базу, фикс, режимы и округления. Выписка загружается общей операцией организации; открытый сейчас кабинет менеджера не влияет на распределение.

Нет ИИ, DeepSeek, OCR, внешнего распознавания, запросов в банк и 1С, новых AI-зависимостей. Нет автоматической загрузки из банка, универсального банковского парсера, PDF/изображений, разделения оплаты между менеджерами, записи в 1С, нового учёта прибыли/себестоимости/налогов. Не переписывать модули и не проводить общий рефакторинг. Существующие CRM ACL, вкладки/workOwners, заметки, контакты, звонки, цвета и фильтры остаются прежними.

## 2. Данные и безопасные миграции

Реализация следует точным границам и именам из `interfaces.md`; окончательные фактические символы после каждого таска добавляются туда до зависимой работы. Выделяются следующие сущности, без второй копии менеджерского ledger:

| Сущность | Содержимое и инварианты |
|---|---|
| Подтверждённый счёт импорта | Существующая наша организация, разрешённый счёт и БИК; админ подтверждает настройку с причиной, если существующий справочник не даёт всех реквизитов |
| Загрузка выписки | Приватный файл, SHA-256, организация/счёт, период, валюта, обороты и nullable остатки, автор/время, состояние/ошибки, версия парсера |
| Строка источника | Загрузка, лист и физическая строка, точные исходные значения/типы ячеек, нормализованные поля, ошибки/предупреждения, ссылка на операцию |
| Банковская операция | Неизменяемые банковские реквизиты и стабильная идентичность в пределах организации/счёта; все повторные строки-источники сохраняются |
| Решение | Классификация/объяснение, выбранный CRM клиент, предложенные менеджер и ставка, предупреждения, ручные подтверждения/причины, версия и аудит |
| Связь продажи | Уникальная связь операции с существующей `manager_sales`, включая возможность 1:1 банковского подтверждения старой manual/onec продажи без переписывания её source |
| История закреплений | CRM клиент, `manager_accounts.id`, интервал действия, автор/время/причина; версия клиентской связи; не ACL |
| Идемпотентный commit | Ключ, хеш канонического содержимого запроса и сохранённый результат в той же транзакции, что проведение |

У новых bank sales источник `bank_statement`, ссылка на CRM и банковскую операцию, снимок наименования `document_name` / `full_name` (совместимый `name` только для старых пустых данных), банковская календарная дата, полная сумма в копейках, ставка выбранного менеджера нужного месяца и manager snapshot. Старые продажи продолжают работать с пустыми новыми связями; клиент/менеджер им эвристически не назначается.

`manager_sales` source CHECK расширяется безопасной миграцией. При пересоздании SQLite-таблицы сохраняются **ID и все существующие поля**, включая реальные `invoice_number`/`invoice_date`, индексы, внешние ключи, версии, аудит и закрытые snapshots. Миграция транзакционна, повторяемая и проверяется на чистой БД, заполненной legacy БД с данными/закрытым месяцем и повторным запуском. Production/рабочая БД не используется.

Непересечение интервалов закреплений обеспечивается проверкой в транзакции и SQLite trigger. Уникальность связи операции/продажи и идемпотентных ключей обеспечивается БД. Все связанные записи создаются через существующий общий механизм менеджерского учёта: внутренний helper принимает текущую SQLite-транзакцию и сохраняет существующие проверки сумм/числа записей, версии периодов и аудит. Публичный ручной API не позволяет подделать trusted bank source/IDs. Финансовую идентичность проведённой bank sale нельзя свободно отредактировать и отвязать от платежа; штатная отмена остаётся доступна с причиной и аудитом.

## 3. Чистый XLSX-парсер и денежные правила

Чистая функция получает bytes и возвращает JSON-совместимые метаданные, строки с source coordinates, нормализацию, ошибки и сверку. Она не знает CRM, БД, storage, 1С и сеть. Используется существующий серверный `openpyxl` стек.

Поддерживается лист «Выписка по счёту» с верхними метаданными и двухуровневой шапкой. Структура находится по названиям полей, а не по фиксированным строкам 13–18; добавление пустых строк не ломает импорт. Неоднозначная/неизвестная структура выдаёт понятную ошибку. Все 13 колонок: дата, номер документа, дебет, кредит, контрагент/наименование, ИНН, КПП, счёт, БИК, наименование банка, назначение, код дебитора, тип документа. Сохраняются исходные ячейки и физические координаты. ИНН владельца и контрагента — разные поля.

Метаданные: владелец счёта, его ИНН, наш счёт/БИК, начало/конец периода, валюта, дебетовый/кредитовый обороты, остатки только если действительно указаны числами. `RUR` → `RUB`; другие валюты сохраняются с блокирующей ошибкой без конвертации/продаж. «—» в остатках означает null, а не ноль, и отсутствие возможности балансной проверки само по себе не блокирует файл.

Деньги читаются из debit/credit ячеек, включая числовые ячейки и корректные тексты с пробелами/десятичной запятой. При разборе применяется `Decimal`, затем целые копейки; денежной арифметики через float нет. Требуются конечные корректные значения без недопустимой точности/отрицательного направления. Нельзя выводить сумму из назначения, делить на НДС или заменять суммой счета. Два частичных платежа дают две фактические суммы; два платежа одного клиента не сливаются.

Дата операции — календарная ISO date без UTC/local time сдвига; месяц продажи берётся из неё. Invoice number/date и платёжный документ/дата операции раздельны. Оплата ноября по сентябрьскому счёту — ноябрьская продажа. Проверяются валидная дата, попадание в период, обязательные поля, направление, отсутствие одновременно положительных debit и credit. ИНН, КПП, счета, БИК, номера документов — строковые идентификаторы с ведущими нулями. Явно испорченные Excel идентификаторы не восстанавливаются догадкой; ошибка остаётся видимой.

Формулы не исполняются и cached value не считается молчаливым основанием критического поля. Формула в дате/сумме/идентификаторе/ином критическом поле отмечает ошибку и блокирует соответствующее проведение. Макросы и внешние ссылки не выполняются. Перед открытием ZIP проверяются лимиты сжатого файла, числа entries, распакованного размера/отношения сжатия, строк, опасные/повреждённые контейнеры; имена paths и XML обрабатываются безопасно. Константы лимитов экспортируются и проверяются на границах.

Суммы **всех** прочитанных операций сверяются с оборотами файла отдельно по дебету и кредиту **до** классификации и отбора sales. При расхождении весь файл не проводится; UI получает expected/read/difference для обеих сторон. Некорректная строка не исчезает из сверки. Соответствие выбранной нашей организации/разрешённого счёта проверяется до проведения; реквизиты образца не hardcoded.

## 4. Сопоставление, классификация и счёт

Основной ключ CRM matching — нормализованный валидный ИНН контрагента с проверкой длины/контрольных цифр; для юридических лиц КПП уточняет неоднозначность. Пустой/ошибочный ИНН не исправляется и не заменяется похожим названием. Название — только дополнительная информация. Если несколько локальных или связанных с 1С карточек совпали, нет выбора первой/автообъединения; операция ждёт решения администратора.

Не найденный клиент: операция сохранена, администратор может выбрать существующего или перейти в штатное создание CRM и обновить результат без повторного файла. Ручное сопоставление с отличающимся ИНН требует предупреждения, admin role и обязательной причины; неизменяемый плательщик и выбранный CRM клиент хранятся отдельно.

Классификация независима от matching. Детерминированные правила сохраняют объяснение:

| Признаки | Предложение |
|---|---|
| Оплата/предоплата покупателя за товары или услуги | Кандидат в продажи, остальные проверки ещё обязательны |
| Собственный перевод, заём/кредит, возврат поставщика, внесение средств, иные непокупательские поступления | Исключено автоматически с объяснением, не sales |
| Противоречивое/неизвестное назначение | Ручная проверка |
| Оплата за третье лицо | Ручная проверка принадлежности |
| Исходящий возврат покупателю | Отдельная операция для проверки и сообщение о ручной корректировке; не отрицательная sale и не автоматическая отмена |

Администратор может подтвердить или изменить классификацию с обязательной причиной, сохранением исходного правила и аудитом. Никаких AI probabilities/уверенности. Найденный клиент не делает любое credit поступление продажей.

Invoice references извлекаются ограниченными проверяемыми шаблонами «по счёту № ...», «счет на оплату № ...», даты цифрами и русскими словами. Номер платежного поручения не считается invoice number. Несколько счетов сохраняются списком/исходным текстом; не выбирается случайный и не дублируется сумма. Невалидная/неоднозначная дата остаётся пустой с предупреждением. Для `№255 ОТ З НОЯБРЯ 2026 Г.` разрешён number `255`, но буква «З» не заменяется на цифру 3. Отсутствие invoice number/date само по себе не блокирует достоверный платёж. Исходное назначение хранится без переписывания; явная ручная проверка/коррекция — отдельное решение с причиной.

## 5. Три уровня дедупликации

1. **Файл:** SHA-256 в пределах import context распознаёт повтор независимо от имени; возвращается существующая загрузка/результат, новые продажи не создаются.
2. **Банковская операция:** устойчивый bank ID, если есть, ограничен организацией/счётом. Без него strict normalized identity включает организацию/наш счёт, валюту, направление, дату, payment document, реквизиты плательщика, сумму, назначение/дополнительные source признаки. Имя файла, sheet/row и период выгрузки не identity. Один и тот же однозначный платёж в недельной/месячной выписке связан со всеми исходными строками. Изменённое назначение/неполные реквизиты дают probable duplicate и обязательное ручное решение. Одни клиент/дата/сумма недостаточны. Разные номера документов и частичные платежи сохраняются отдельно. Несколько неотличимых одинаковых строк в одном источнике **все сохраняются**, группа блокируется до явного решения, второй реальный платёж не исчезает.
3. **Старые manual/onec продажи:** ищутся возможные совпадения по client, amount, date, invoice/доступным реквизитам. Администратор выбирает: 1:1 связать без увеличения итога; подтвердить отдельную новую оплату с причиной; оставить review. Исторический source не меняется. Link разрешён только при согласованных полной сумме, конкретном клиенте и manager account; legacy client text требует явного подтверждённого точного сопоставления, не автоматической эвристики. Сводные продажи и несколько оплат не дробятся автоматически. Уже связанная sale или операция не линкуется второй раз.

Unique constraints и транзакции защищают все новые связи и sales независимо от UI/idempotency key. Отменённая bank sale остаётся связанной с исходной операцией: её reload или новый ключ не восстанавливает и не возвращает в новые.

## 6. Закрепление, durable preview и права

Закрепление — отдельная общая связь CRM клиента с `manager_accounts.id`, не `users.id` и не workOwners/вкладки/автор/цвет/crm_owner_user_id. Менеджер выбирается только активный, через `manager_accounts.user_id → users.id`; несовпадающие ID — обязательный тест. Интервалы `[startDate, endDate)` не пересекаются. Начальная дата обязательна; UI предлагает сегодня и позволяет явно выбрать прошлую для первоначального заполнения/исправления. Смена/снятие с выбранной даты корректирует содержащий дату интервал или вставляет в промежуток до следующего, сохраняя историю и непересечение. Хранятся автор, время, причина и версия. Изменять может только администратор.

На дату операции выбирается единственное действующее закрепление. Неактивный/удалённый сотрудник и архивный клиент блокируют предложение с причиной; другой менеджер не подставляется. Изменение закрепления автоматически обновляет только **ожидающие** предложения клиента, возвращает количество, период и полную сумму; проведение остаётся отдельным подтверждением администратора. Ни ручные, ни bank исторические продажи/зарплаты не переносятся и не пересчитываются.

Загрузка/парсинг/preview сохраняют исходные данные и решения, не создают `manager_sales`; reload/restart возвращает незавершённую работу. Refresh повторяет matching/classification/readiness. Каждый decision имеет версию и fingerprint зависимостей: assignment/client/account/manager availability, точные month terms и состояние/версию периода, duplicate candidates и manual decision. Ставка из явных условий менеджера месяца оплаты; отсутствие условий — pending blocked, ноль допустим. Закрытый месяц — pending blocked без автооткрытия; после штатного открытия доступен refresh.

Backend роль администратора обязательна для upload/download полного файла, общего журнала/истории, подтверждения, настройки счёта, закрепления и ручных решений. Все direct ID endpoints проверяют права, включая клиентские/operation/file IDs. Менеджер видит свои проведённые продажи и только разрешённые ему сведения платежей; не получает чужие salary/rates/totals/полные реквизиты/raw purpose/исходный общий файл через CRM. Обычная CRM ACL проверка сохраняется; новая sales relation не открывает доступ к персональным данным.

Исходник хранится приватно вне public/shared customer documents; выдача только авторизованным admin endpoint, не публичный URL. Используется existing storage root и backup с отдельным закрытым namespace. File limits проверяются до дорогого parse, role — до reading/parsing. Ответы приватных API no-store. В обычных логах нет текста выписки, банковских реквизитов и содержимого. Ошибки понятные, без traceback/секретов.

## 7. Атомарное проведение и вознаграждение

Выбранные ready операции могут быть проведены отдельно; остальные остаются видимыми pending. Сервер под `BEGIN IMMEDIATE` до записи **повторно** проверяет admin role, decision versions/fingerprints, assignment на дату, availability клиента/manager, условия нужного месяца (включая ноль), состояние/версию месяцев, file reconciliation и duplicates. Изменение после preview — `409` с предложением обновить результат; по старым условиям молча не проводить.

Весь выбранный пакет (sale/link, audit, period versions, decision state, idempotency record) коммитится одной транзакцией или откатывается целиком. Общий внутренний manager helper обеспечивает существующие доменные validation/лимиты количества и суммы/audit/versions; отдельный обходной INSERT запрещён. Сохраняется ставка каждой sale. Существующий `calculate()` рассчитывает before/after totals, commission и income для каждого затронутого manager/month. Эти эффекты показываются до подтверждения и повторно валидируются.

`idempotencyKey` привязан к canonical payload hash выбранных operation IDs/versions/fingerprints. Одинаковый retry после двойного клика, потери ответа или рестарта возвращает сохранённый результат. Тот же key с другим payload — 409. Новый key не обходит unique operation linkage. Два администратора не проводят одну оплату дважды: serialized transaction + unique DB constraints. Любая ошибка последней строки откатывает весь selected set. Preview не пишет ledger.

Отмена импортированной sale — штатная с причиной/аудитом и учётом открытости периода. Операция, строка, файл и связь остаются; нет auto reactivation при reload. Исторические snapshots закрытых месяцев не редактируются. Возвраты только обозначают ручную корректировку и не создают отрицательные продажи.

## 8. Интерфейс, API и кеш

API namespace `/api/bank-statements`, точные endpoints/payloads/ownership в `interfaces.md`. Добавочные API не затрагивают unrelated contracts. `bank-types.ts` отражает фактический backend, authenticated `api.ts` методы соблюдают существующую обработку auth/errors. После assignment/commit выполняется целевая инвалидация/refresh manager workspace и CRM payments; totals не остаются устаревшими.

В существующих продажах администратору доступны «Загрузить выписку» и история. Выбор подтверждённой организации/счёта и при необходимости admin explicit account config. Загрузка единая независимо от открытого менеджера. История переживает перезагрузку, даёт открыть preview/скачать исходник администратору и обновить решения.

После upload показываются организация, счёт, валюта, период, число операций, входящие/исходящие обороты и reconciliation expected/read/difference; число/сумма ready, accounted, review, excluded. Строка/мобильная карточка: дата, плательщик, ИНН, сумма с НДС, invoice, клиент, manager, статус/причина. Purpose и banking details раскрываются отдельно. Статусы: готово; клиент не найден; несколько совпадений; менеджер не назначен; нет условий месяца; возможный дубль; уже учтено; месяц закрыт; требуется проверка назначения; исключено; ошибка данных. Архивный клиент/неактивный менеджер показываются понятной причиной.

Есть admin client picker и переход в штатное создание; ручная классификация, исключение, invoice correction, duplicate new/link/review требуют reason там, где меняется решение, с предупреждениями и последствиями. Неопределённость не маскируется «уверенностью». Выбор ready rows, effects по каждому manager/month и основная кнопка «Добавить N оплат на … ₽ с НДС». Во время confirm повтор исключается, idempotency key переживает безопасный retry; 409 предлагает refresh. После частичного успеха проблемные строки не скрываются.

В CRM desktop/mobile общий sales panel: «Менеджер по продажам», «Оплаты клиента засчитываются этому сотруднику», дата начала; администратору active account picker, mandatory start date/reason, снятие, version conflict и история изменений, pending count/range/gross amount после назначения. Поступления — те же операции/sales, не копии; дата, сумма с НДС, invoice, manager и состояние учёта. Менеджеру — только разрешённые own posted receipts без зарплатных деталей других.

В existing manager sales появляется source label «Банковская выписка», прежние графики, totals, поиск, пагинация и формулы сохраняются. Нет общего redesign. На 390 × 844 CSS px и desktop UI проверяется на synthetic data: компактные cards/rows, раскрытие, видимая сумма/клиент/manager/problem, нет обязательного огромного x-scroll, confirm не закрывает content/нижнюю навигацию. Существующие фильтры/звонок/colors/персональные вкладки CRM не меняются.

## 9. Исполнение, публикация и безопасность среды

Свежий `origin/main`, изменения после указанного base проверены, task branch `codex/bank-statement-manager-sales` и отдельный worktree. Нельзя reset/stash/clean/rebase/force-push или удалять чужую работу. Краткий план и миграционная схема до product code: T01 foundation/history/common transactional helper; после T01 параллельно T02 pure parser и T04 UI по фиксированному API; после T02 — T03 durable workflow/API/security/private storage; после T03/T04 — T05 acceptance/docs/screenshots. На каждом этапе сначала тест требуемого поведения, реализация, затем фактический affected check. Независимый whole-branch review один по применимой owner policy; чистый review не повторяется ради ритуала.

Готовый Python/node_modules разрешено переиспользовать при изоляции task data/build/cache, но не runtime settings/DB/storage/1С. Все тесты на временных БД/storage с synthetic Fernet key; E2E только через documented npm isolated launcher/allowlist. Не передавать рабочие настройки 1С. Никаких запросов к рабочей 1С и внешнего recognition. Реальная выписка, рабочая БД, secrets, реальные client requisites/financial screenshots не коммитятся. Synthetic data сохраняет структуру и контрольные суммы, не реквизиты оригинала.

PR готовится по действующим правилам, без нового Actions gate/CI. Явный бриф запрещает merge без отдельного разрешения; разрешение на commit/push/PR не равно разрешению на merge. Позднее «Если все зеленое деплой» — conditional owner authorization на выпуск после фактических зелёных checks. Оно не отменяет запрет менять чужие production data/DNS/контейнеры/1С и safeguards release workflow. Перед любым выпуском проверяются внешние автоматические триггеры, доступный согласованный контур, точный main SHA, действующий runtime SHA/health, проверенный backup и восстановимый откат. Sites/Vercel исключены. Если для получения main SHA остаётся запрет merge или не согласован контур/backup, ведущий доводит PR и evidence до reviewable результата и запрашивает только точное защищённое действие; не объявляет deploy выполненным. Рабочую БД/production в разработке не изменять.

## 10. Проверки и критерии приёмки

Контрольный synthetic XLSX содержит 6 credits и 5 валидных synthetic payer ИНН; документы/суммы/invoices: `2810/360000/256`, `577/680000/257`, `5471/22000/216`, `606/164000/255`, `847/246000/252`, `846/517063/241`. Invoice 216 от 09.09.2026, sale всё равно ноябрь; 255 с «З НОЯБРЯ» — date null + warning. Остатки «—» null. Credit total **198906300 коп. / 1 989 063,00 ₽**, debit total 0.

Повтор файла с другим именем/тот же commit создают 0 sales, totals неизменны.

Обязательные интеграционные сценарии (не считать source-text или зеркальные unit tests достаточной заменой):

- Gross VAT сохранён; sale date из операции, не invoice/upload; разные calendar dates без timezone сдвига.
- Unknown/invalid ИНН; несколько CRM совпадений; КПП disambiguation; empty ИНН не name match; ручной mismatch reason/admin.
- Missing/inactive/deleted manager, archived client; manager/account user IDs различаются; intervals nonoverlap, backdate, transfer across periods, снятие; старые sales не перемещаются.
- Missing month terms, явно zero rate, ставка нужного месяца; прежние payroll modes/rounding/totals.
- Два частичных платежа одного invoice; same amount/date/client с разными payment docs; неоднозначные одинаковые строки не теряются.
- Same file renamed; overlapping week/month; changed purpose/incomplete identity probable duplicate; stable bank ID при наличии.
- Existing manual/onec candidate, 1:1 link без увеличения totals/source rewrite; separate new confirmation; запрет inconsistent amount/client/manager/link reuse и aggregate splitting.
- Cancelled bank sale не resurrected; own transfer/loan/credit/supplier return/deposit excluded; unknown/contradictory/third-party review; buyer return без negative sale/auto cancel.
- Terms/assignment/client/manager/closed period меняются после preview → 409; opening штатно позволяет refresh, snapshots неизменны.
- Два администратора одновременно; response loss retry; restart retry; same idempotency key с иным payload → 409; новый key не дублирует operation; весь selected batch rollback при последней ошибке.
- Частичное проведение не теряет pending; unfinished import survives repository/API restart; assignment автоматически refresh pending count/period/gross, не проводит.
- Reconciliation mismatch блокирует файл и показывает обе стороны; omitted balances null; wrong organization/account; bad direction/date/period/currency.
- Изменённый/неоднозначный формат, corrupt ZIP/XML, compressed/unpacked/row limits, formula критического поля, macros/links безопасно отклоняются/не исполняются; numeric/text amounts/leading zeros.

- `DEEPSEEK_API_KEY` отсутствует и 1С недоступна — import работает; network calls к DeepSeek/банку/рабочей 1С отсутствуют.
- Browser acceptance desktop и 390 × 844 на synthetic data: полный admin journey, history resume, pending visible, manager own sale source, CRM assignment/payments и UI safety.
