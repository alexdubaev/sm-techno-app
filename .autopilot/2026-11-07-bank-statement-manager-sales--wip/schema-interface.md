# T01 — фактическая схема и вызовы

Миграция `2026-11-07-bank-statements-v1` в `WebDatabase.WEB_MIGRATIONS`, реализация `stock_sync_web.bank_schema.migrate(conn)`, проверка `migration_present(conn)`. Все SQL statements выполняются внутри существующей migration transaction. Денежные поля INTEGER (копейки), rate INTEGER (базисные пункты). Date strings календарные ISO; timestamps UTC ISO. JSON хранится TEXT, сериализация ensure_ascii=False.

## Таблицы (полный DDL — bank_schema.py)

- `bank_import_accounts`: id, organization_id FK organizations, organization_name, owner_inn, account, bik, currency='RUB', active=1, version=1, created_by, created_at, reason. UNIQUE(organization_id,account). ИНН и название снимком в настройке, известный ИНН организации должен точно совпасть; отсутствующий разрешено явно подтвердить без изменения справочника.
- `bank_uploads`: id, account_id FK bank_import_accounts, sha256, original_filename, storage_key UNIQUE, byte_size, parser_version, metadata_json, errors_json='[]', reconciliation_json='{}', state='parsed', created_by, created_at. UNIQUE(account_id,sha256). `storage_key` opaque, относительный; файловую запись/backup интегрирует T03.
- `bank_operations`: id, account_id FK import account, organization_id FK organizations, our_account, currency, direction ('credit'/'debit'), date, document_number, payer_name, inn='', kpp='', account='', bik='', bank_name='', amount>0, debit>=0, credit>=0, purpose, debtor_code='', document_type='', bank_id nullable, strict_key, probable_key, invoice_references_json='[]', normalized_json='{}', created_at. CHECK направление/amount/debit/credit согласованы; деньги строго typeof integer. Имена полей snake_case для хранения, camelCase для API. `strict_key`/`probable_key` индексированы НЕуникально: одинаковые неоднозначные строки не теряются. UNIQUE(account_id,bank_id) только при nonnull bank_id. UPDATE всей записи запрещён SQLite trigger; ручные поправки хранятся решением.
- `bank_source_rows`: id, upload_id FK upload, sheet, row_number, raw_json, normalized_json, errors_json='[]', warnings_json='[]', operation_id nullable FK operation. UNIQUE(upload_id,sheet,row_number). Каждая исходная строка сохраняется, в том числе некорректная без операции; повторная строка пересекающейся выписки ссылается на ту же operation только при однозначности.
- `bank_decisions`: operation_id PK/FK operation, version=1, classification='review', explanation='', client_id nullable FK CRM, manager_id nullable FK manager_accounts, rate nullable, status='review', warnings_json='[]', manual_json='{}', decision_json='{}', fingerprint='', reason='', updated_by nullable, updated_at required. `manual_json` — подтверждения/исправления, `decision_json` — дополнительные рассчитанные данные/candidates, конкретные ключи T03. Нет CHECK списка статусов/классификации: доменные правила T03.
- `bank_decision_audit`: id, operation_id FK, actor_id, at, reason, before_json, after_json.
- `bank_sale_links`: operation_id PK/FK operation, sale_id UNIQUE FK manager_sales, client_id FK CRM, manager_id FK manager_accounts, amount>0 integer, kind ('created'/'existing'), linked_by, linked_at, reason. Link не удаляется при cancel. Совместимость amount/client/manager и общий ledger audit T03 проверяет в одной transaction.
- `bank_commits`: idempotency_key PK, actor_id, request_hash, response_json, created_at. Вставка в той же transaction, что sales/links.
- `crm_sales_assignments`: id, client_id FK CRM, manager_id nullable FK manager_accounts, start_date, end_date nullable, created_by, created_at, updated_by, updated_at, reason. Интервалы [start,end), null manager — явное снятие. UNIQUE(client_id,start_date); CHECK end>start; BEFORE INSERT/UPDATE SQLite triggers запрещают пересечение, включая null-manager интервалы.
- `crm_sales_assignment_versions`: client_id PK/FK CRM, version=0.
- `crm_sales_assignment_audit`: id, client_id FK, version, actor_id, at, reason, before_json, after_json. before_json — весь список старых интервалов; after_json={intervals:[...],changedAssignment:{...}}. Снимки включают manager_name на момент изменения. Эта история сохраняет и замены на ту же start_date.

## Продажи и миграция

`manager_sales` сохраняет все прежние поля + `crm_client_id` nullable FK CRM + `bank_operation_id` nullable FK operation. source CHECK расширен `bank_statement`; UNIQUE(source,external_id) сохранён. Новые индексы `manager_sales_bank_operation` UNIQUE WHERE operation nonnull и `manager_sales_crm_client`. Rebuild копирует фактическую DDL/все колонки, повторно создаёт существующие SQL indexes/triggers и сохраняет максимальный sqlite_sequence даже после удалённой строки. Старым продажам ничего не сопоставляется.

`ManagerRepository._mutate_in_transaction(conn, actor, manager_id, month, payload, *, bank_operation_id=None, crm_client_id=None)` требует открытую transaction; публичный `mutate` пользуется тем же методом. Возвращает прежний dashboard + внутренний `changedSaleId` при sale/cancel; публичный mutate удаляет дополнительный ключ. Payload прежнего manager API, в том числе kind='sale', version (актуальная версия месяца), reason, date, client, amount, rate, invoiceNumber/invoiceDate.

Для bank create передать оба trusted keyword IDs. Helper повторно проверяет admin, существующий период/version/open, active user через manager_accounts.user_id, client available, действующее assignment на date, RUB credit operation с точной датой/полной суммой, terms присутствуют и rate равен rate месяца. Snapshot client вычисляется из document_name/full_name/name fallback. Source/external_id/CRM/op записываются только trusted path (external_id=str(operation_id)), затем прежний count/money limits, period increment и audit. Старые payroll calculate/snapshots сохранены. Обычный HTTP payload не может подставить trusted kwargs.

Любая sale с source=bank_statement или существующим bank_sale_links запрещена для обычного редактирования; cancel разрешён прежним механизмом и аудитом. Helper не вставляет `bank_sale_links`: T03 создаёт его из changedSaleId в той же outer transaction. При нескольких платежах одному manager/month каждый следующий вызов получает новую текущую version. Rollback outer transaction откатывает все sales, audits и versions. Preview T03 делает rollback/savepoint сам; helper ничего не коммитит/не откатывает.

В текущем sales DTO и новых close snapshots поле `bankOperationId` равно собственной `manager_sales.bank_operation_id`, иначе operation_id из bank_sale_links, иначе null. Это позволяет скрывать edit и для исторической manual/onec sale с подтверждённым банковским link без изменения source. Старые сохранённые snapshots не переписываются.

## BankAssignmentRepository(db)

- `accounts(actor)` admin → HTTP `{organizations,accounts}` по frozen DTO.
- `confirm_account(actor, organization_id, owner_inn, account, bik, reason)` admin → account DTO. Проверяет строковые digits lengths, INN checksum, известный org INN, обязательную причину. Повтор тех же реквизитов возвращает тот же id; другие реквизиты/disabled setting → conflict. Нет 1С запросов.
- `client_assignment(actor, client_id, at_date=None)` admin → DTO clientId/version/assignment/history/payments=[]/pending. По умолчанию сегодняшняя календарная дата Москвы. Payments заполняет T03.
- `set_assignment(actor, client_id, manager_id|null, start_date, reason, version, *, refresh_pending=None)` admin → тот же DTO, одна immediate transaction. Версия 0 при первой записи. Настраивает только интервал, содержащий start_date, либо промежуток до следующего будущего интервала; заданные будущие передачи сохраняются. Старые продажи не трогает.
- `_set_assignment_in_transaction(conn, actor, client_id, manager_id, start_date, reason, version, *, refresh_pending=None)` тот же механизм при существующей outer transaction.
- `assignment_at(conn, client_id, on_date)` static internal → raw interval dict snake_case + manager_name/user_id/manager_active; None если нет. Это не authorized disclosure API; T03 перед выдачей проверяет существующий CRM ACL.
- `pending_summary(conn, client_id)` static → `{count,amount,periodStart,periodEnd}` для unlinked credit decisions этого client, classification не excluded/return.
- `_client_assignment(conn, client_id, at_date=None)` internal formatter без проверки доступа: вызывающий обязан проверить клиента/роль.

## Callback автоматической переоценки

При assignment обновляются version/fingerprint только unlinked bank_decisions указанного client: version+1, fingerprint='', updated_by/at. Старый preview непригоден. Затем внутри той же transaction вызывается `refresh_pending(conn, client_id)`, если передан. **T03 обязан передать callback полного доменного re-evaluation**, включая сохранённые unmapped операции с ИНН клиента, matching, assignment на operation date, terms, duplicate/closed checks и объяснения. Callback не проводит продажи и не коммитит. Это позволяет вернуть новые готовые предложения/summary сразу, сохранив atomicity assignment+refresh. Без callback foundation только безопасно инвалидирует старый preview и возвращает count/период/сумму, не выдумывая статус ready.

## T03 — банковское подтверждение старой продажи через общий ledger

`ManagerRepository.record_bank_link_in_transaction(conn, actor, manager_id, month, expected_version, sale_id, reason, operation_id)` работает только в открытой outer transaction. Проверяет admin, выбранный account/active user, month open/version/terms, noncancelled source manual/onec sale указанного manager/month без прежнего bank link; RUB credit operation с той же датой/полной суммой; persisted bank_decisions.client_id/manager_id; доступность клиента и effective assignment на дату операции. При nullable sale.crm_client_id требует точного нормализованного document_name/full_name snapshot (name только когда оба документных поля пусты); с ненулевым CRM id требует его совпадения. T03 дополнительно проверяет ручное решение и mismatch reason.

Метод **не меняет ни одного поля manager_sales**, включая source, crm_client_id, rate и updated_at. Старая ставка сохраняется, даже если текущие terms.rate другие. Salary totals/commission/income не изменяются. Обновляется только manager_periods.version и добавляется manager_audit.kind=`bank_link`, с обязательной причиной, неизменными before/after sale snapshots и root after.bankOperationId. Закрытые сохранённые snapshots не трогаются. Возвращает dashboard + changedSaleId. T03 вставляет `bank_sale_links(kind='existing')` после вызова в той же outer transaction; rollback обязан откатить и link, и этот audit/version. Метод ничего не коммитит.
