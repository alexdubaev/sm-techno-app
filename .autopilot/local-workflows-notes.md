## Expanded UX decisions and seams (2026-10-30)

User direction supersedes the earlier UI placement: `/documents` owns create contract/specification, archive upload, and journal access; CRM card only related document list, versions and download. Upload source first, then confirm client; invoice source DOCX only. Stock produces an offer without a client, attach later. This is discovery only, not an implementation authorization for schema/API/1C changes.

### Stock → offer without client → attach later
`WebService.create_commercial_offer_from_draft(*, client_source,client_id,client_name,notes,lines,created_by_user_id)` generates XLSX, stores snapshot plus lines atomically with compensating cleanup. POST `/api/commercial-offers/from-draft` accepts `clientSource`, `clientId`, `clientName`, `notes`, `lines`. Database `commercial_offers.counterparty_id` and `crm_client_id` already nullable; `client_name_snapshot TEXT NOT NULL` permits empty text structurally. Nevertheless `_resolve_commercial_offer_client` rejects empty manual name and requires local/onec ID, and current reviewed article offer requires client and immediately creates it. No offer attach/update endpoint was found; only `mark-sent` and admin delete. Owner/admin offer authorization is enforced by `get_commercial_offer_for_user`; offers are private to creator/admin, unlike shared manager documents.

A real unbound offer therefore requires a deliberate supported state/validation and new protected mutation to attach a confirmed client, with transactional no-overwrite/conflict/race rules and existing owner/admin ACL. Schema migration is not obviously required for nullable IDs, but verify assumptions and desired constraints in a confirmed plan; do not use a fake client name. Choose whether generated XLSX is a historical unbound snapshot or must be regenerated/updated on attach; otherwise metadata and downloaded workbook disagree. Define what happens for already-sent offers and repeated/concurrent attach before implementing. Attach must resolve allowed canonical identity without leaking private CRM details. Generation from reviewed unbound article job should reuse existing stock resolution and safe offer creation/idempotency; review is explicit confirmation before creation. Treat changes as protected API/persistence work.

### Unbound source → match and confirm canonical client
`AssistantRepository.match_document_identity(card)` matches exact legal entity INN+KPP or individual entrepreneur INN against local CRM and cached counterparties. It rejects duplicates, archived CRM identity and conflicting links; it returns `(client_id, cached_counterparty)` and does not itself call 1C. A narrow document-purpose candidate read can return only ID, document name, INN/KPP and minimal status after the job ownership/review check; do not expose CRM notes, contacts or activities or relax CRM endpoint ACL. `DocumentAssistantService._validate_document_client_identity(client_id,card)` checks immutable identity; `get_client_display` checks ambiguous linked counterparties. Extractor receives only source file content through `ExtractionRequest(kind,texts,images,source_asset_ids)`; model must not receive private CRM records.

`confirm_extraction(actor,job_id,expected_version,fields,operation_key,action)` → `confirm_requisites(actor,job,expected_version,fields,operation_key,action)` with `action='create_client'` or `'generate_contract'` normalizes reviewed legal identity, checks canonical contract state, claims idempotent operation, calls `_resolve_reviewed_client(actor,job,card)`, then atomically `bind_reviewed_job(job_id,actor_user_id,client_id,expected_version)` and optionally generates the contract. Resolver finds local/cached identity; cached or remote lookup can create minimal catalogue-linked CRM card; otherwise strict 1C identity lookup precedes `service.create_client(actor_user_id=...,payload=card,on_local_created=...,strict_identity=True)` which creates local card then sends to 1C or records sync_error/not_sent. Unknown outcomes block unsafe retries. Thus current confirmation does more than lookup: it may create CRM card and write 1C; do not invoke merely to show a proposed match. Client confirmation and any 1C write must be explicit, preserve existing guard and do not perform in tests.

Invoice currently `intake(...,'invoice',file)` can be unbound and generic review can confirm it, but `generate_specification(actor,client_id,invoice_job_id,operation_key)` demands `job.clientId == client_id` and client-bound DOCX asset. Existing repository `bind_reviewed_job` has ownership/version rules but no public generic binding endpoint; it needs a narrowly scoped explicit confirmation adapter with validated matching of reviewed invoice buyer INN/KPP/name to chosen client and existing contract, no silent binding or private CRM disclosure. If no match or ambiguous identity, stop for user selection/confirmation; user has not specified whether an unknown buyer should create a CRM/1C client, so do not silently create it. No downstream generation until confirmation.

### Journal and document IDs
Journal `/documents/journal` uses GET `/api/documents` and `GeneratedDocument.id` from shared `documents` table; link currently `/crm?documents={crmClientId}` (client id, not document or source id). The same `documents.id` is used by `GET /api/documents/{id}/download` to retrieve current `output_path`. `client_document_assets.id` is a different ID namespace; `GET /api/document-assets/{asset_id}/download` returns a specific saved version/source, and rows point to `document_id`. `add_version` updates current document output path, preserving prior assets; journal download thus serves current version. CRM panel lists assets and uses both endpoints. `list_documents_for_user` currently reads all documents for managers; client document repository uses linked canonical client/counterparty association. Moving the UI must reuse this shared repository rather than duplicating records; use a document ID for deep links if needed and keep client ID distinct from source asset ID. Archive import currently requires client-bound asset and explicit number/date; file-first flow needs safe explicit binding of unbound archive asset or defer upload until client confirmed, without losing selected file.


## G05 — временная расценка без хранилища
Решение владельца заменяет все вышеописанные предложения о создании КП и поздней привязке: stock загружает список артикулов, получает временную расценку и XLSX; КП пользователь создаёт сам в прежнем клиентском процессе. Никаких durable intake/jobs/assets, записей подборки или журналирования исходников/строк/результатов. Клиент хранит файл/подтверждённые строки/результат только в памяти вкладки, без localStorage/URL/IndexedDB. При refresh состояние теряется.

Существующие изолированные швы без репозитория: `DocumentSourceReader(limits=UploadLimits()).read(path: Path, workspace: Path) -> (texts, image_paths)` проверяет `_validate_file`, размеры/структуру, парсит xlsx/xls и форматы. `CodexDocumentExtractor.extract(ExtractionRequest(kind='articles', texts=texts, image_paths=images, source_asset_ids=[]))` возвращает `ExtractionResult`; `validate_payload('articles', result.payload, partial=...)` обязательно применять даже к injected adapter. `source_asset_ids=[]` исключает фиктивную provenance, reader и extractor сами не обращаются к БД. Прямое использование `DocumentAssistantService.intake/start_extraction` запрещено для этого сценария: создаёт записи и private assets. `LocalPrivateDocumentStore.stage_upload` использует постоянный staging в storage; вместо этого bounded stream в отдельном task-only `TemporaryDirectory` с безопасным суффиксом и finally/context cleanup, без имён исходника/данных в логах. Reader/extractor создают временные файлы внутри workspace и own TemporaryDirectory; учитывать OS crash и принудительное завершение: обычный finally не гарантирует cleanup после падения процесса, поэтому требуется безопасное task-scoped удаление осиротевших временных каталогов/TTL или документированная граница, без затрагивания чужих файлов. Не писать raw exception; текущий `ExtractionError` по умолчанию обещает сохранённый источник — заменить внешнее сообщение для transient потока. Синхронный запрос может удерживаться до extractor timeout (до 300 сек), нужен bounded timeout/concurrency и корректные отмена/ошибка без durable job.

## G06 — совпадения и экспорт
`stock_sync_desktop.database.lookup_stock_articles(articles: Iterable[str]) -> dict[normalized sku,list[variant]]`: read-only exact normalized matching, местные товары, активные склады, физический остаток и цена; включает нулевые для отличия от отсутствующих, не учитывает резервы и ничего не меняет. Ключ `_normalize_stock_sku`; строки нескольких разных item_id неоднозначны, различать отсутствующие и нулевые, повторные, положительные склады и цену; алгоритм source `generate_article_offer` можно выделить как pure helper без offer/idempotency/job. Товар с `requested_qty=null` корректен: схема требует ключ с `null`, `validate_payload` его пропускает, предыдущий helper показывает полный остаток; SKU-only xlsx не должен требовать количество. `partial=True` допускает отсутствие ключа, но канонизировать к null и валидировать строки, source_row, лимит и положительные конечные количества, не угадывать данные.

Шаблон `assets/templates/client_price_template.xlsx`, `stock_sync_desktop.excel_tools.export_client_price(path, rows, *, template_path)` — фактический шаблон наличия; `WebStockSyncService.export_client_price_bytes(...)` фильтрует каталог по складам, создаёт временный XLSX и удаляет файл в finally. Вход нуждается в адаптере к `sku`, `category_name`, `print_name/name`, `quantity/row_quantity`, `price`, `warehouse_name/row_warehouse_name`; exporter создаёт отдельные строки по складам и F=Склад. Он не генерирует Excel-комментариев по складам: единственный исходный комментарий шаблона H11 — инструкция вставить артикулы; в строках шаблона до 18810 есть исходные примеры и формулы справа, текущая функция очищает A:F, обновляет диапазоны формул, так что проверить утечки исходного шаблона и вычисление на конкретном output. Требуемые пользователем комментарии с разбивкой по складам требуют нового адаптера (или точечного расширения exporter), не утверждать, что они уже есть. Решить представление нескольких складов согласно назначению: видимые значения/цены и информативный Excel-комментарий не должны скрывать неоднозначность; значения хранятся из свежего snapshot.

`DocumentSourceReader._cell_text` сохраняет текст как есть, а числовое значение с простым форматом `0{2,30}` восстанавливает ведущие нули; введённые Excel числом нули без формата необратимы, не придумывать. XLSX reader использует `data_only=True`, поэтому формулы дают cached value либо пусто, а не проверяются как формулы: для списка SKU нужна политика отклонения формул или явного контролируемого handling, а не молчаливое доверие cached значению. Экспорт текущего client-price напрямую записывает строки и не защищает от Excel formula injection: отдельно принудительно записать все недоверенные строки как текст, включая SKU, названия, бренды, имена складов/комментарии, ведущие пробелы и `= + - @`; `crm_export._safe_text` демонстрирует защиту, при этом учитывать сохранение точного SKU (текстовая ячейка, number_format '@') и корректное представление в Excel. Не нейтрализовать намеренные формулы доверенного шаблона, не записывать пользовательский текст как формулы.

## G07 — ограниченный план API и проверки
План, не существующий API: authenticated stateless multipart upload → чтение/распознавание → JSON строки для явной проверки (без jobId/assetId); затем stateless POST с проверенными строками → свежий stock lookup и JSON результата, и отдельный stateless POST с проверенными строками → свежий lookup + XLSX bytes (не доверять присланным клиентом ценам/остаткам). Возможен один завершающий запрос расценки+XLSX, но если показывается предварительная расценка, объяснить риск изменения остатков и использовать свежий snapshot при экспорте. Обе конечные точки повторно проверяют форму/лимиты/роль; no-store заголовки, redacted errors, без access/request-body логирования, истечение/очистка temp на успех, ошибку и отмену; исключить создание CRM/КП/ассистент-таблиц, 1С и записи склада. Новые API и границы безопасности требуют согласованного protected-плана по AGENTS, а не только UI-правки.

Ценные интеграционные проверки на изолированной БД/файлах и fake extractor без сетевых/1С записей: файл только SKU, text и числовой формат 00000, null qty, полные/отсутствующие/нулевые/неоднозначные и несколько активных складов/цен; формульный вход и экспортные строки `= + - @`/пробелы проверять через openpyxl; template и warehouse comments, внешний вид/точные значения output, без посторонних строк; ошибка extractor/повреждённый файл/лимит/отмена освобождают task temp и не создают записи, проверка ACL и no-store и логов без payload, повторные вызовы без side effects. Проверить что никакая provenance/job/asset/offer запись не создана, физический stock не изменился. Frontend targeted flow drop/select → review → XLSX → reset/refresh без persistent browser storage, без клиента и КП. Проверки предложены, в этом исследовании не запускались.
