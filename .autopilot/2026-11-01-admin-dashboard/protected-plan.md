# План защищённых изменений — проект для согласования

Статус: ПОДТВЕРЖДЁН владельцем 2026-11-01 ответом «5. Да» и разрешением действий API/деплоя в текущей сессии. OData только подготовить; DeepSeek токены/запросы/баланс; планы как в существующем кабинете; все неотменённые продажи включать. Точные правила в spec.md/interfaces.md. Существующие safeguards остаются.

## 1. Агрегаты администратора

Добавить серверный API чтения обзора компании и использования DeepSeek под отдельным /api/admin/dashboard prefix. Использовать существующую проверку активной сессии и роли admin, не менять роли, сессии, пароли или права существующих методов. Менеджеру/анонимному пользователю данные недоступны и при прямом HTTP-запросе. Cache-Control: no-store. Старые /api/manager endpoints и их формы ответа сохраняются.

Агрегаты продаж читать из существующих manager_sales/manager_accounts/manager_periods, суммы в целых копейках. Поля period (kind, start, end), totals, series, managers, plan coverage, sources. Не формировать дашборд клиентским обходом чужих кабинетов. Фильтр периода строгий, диапазон ограничен одним выбранным календарным годом/кварталом/месяцем/неделей; текущий период по Москве. Согласовать состав продаж и формулу плана до фиксации контракта.

## 2. Безопасный числовой учёт DeepSeek

DeepSeek уже работает на сервере и ранее проверен реальными вызовами. План не включает повторную миграцию обработчика, ввод ключа, возврат к Codex или изменение provider/model. Новое здесь — сохранение числовых метрик для дашборда; текущий extractor уже использует внешний DeepSeek API.

Добавить зарегистрированную идемпотентную миграцию: отдельная таблица deepseek_usage с временем UTC, моделью, исходом запроса, prompt_tokens/completion_tokens/total_tokens. Неизвестные токены NULL, а не 0. Индекс по времени. Начало наблюдения отдельно зафиксировано метаданными миграции/учёта. Не хранить ключи, запросы, ответы, тексты, имена файлов, содержимое документов, идентификаторы клиентов или сотрудников.

Внедрить явный общий приёмник метрик в существующий DeepSeek adapter и все пути его вызова (Документы и Расценка, включая мобильные входы через существующие маршруты). Не менять внешний ExtractionResult и результат распознавания. Одна запись на одну фактическую попытку сетевого запроса; до-сетевые ошибки конфигурации/файла не считать запросами. Сохранять usage валидного envelope до проверки содержимого модели, чтобы не терять расход при некорректном результате. Не добавлять повторы внешних запросов.

Сбой записи метрик не должен ломать распознавание; фиксировать только безопасный технический признак ошибки и явно отмечать неполноту учёта. Нет исторического backfill, выдуманных токенов или удаления старых данных. Существующие таблицы продаж, документы, настройки, данные и устройства не переписываются. Новая небольшая числовая таблица сохраняется без автоматической очистки; отдельную политику удаления не добавлять.

## 3. Баланс DeepSeek

Отдельный backend-only GET к фиксированному https://api.deepseek.com/user/balance с существующим DEEPSEEK_API_KEY. Ограничить таймаут и размер ответа, проверять TLS, не следовать redirects/прокси окружения, не отдавать браузеру сырой ответ/ключ/ошибки с секретами. Кэшировать кратко на сервере и показывать время получения, различать unavailable и реальный нулевой баланс. Запрос баланса выполняется для администраторского обзора, без фонового расписания и без платной генерации текста. Баланс аккаунта не выдавать за расходы только СМ ТЕХНО.

График расхода основан на измеренных запросах приложения. Отсутствие истории до включения учёта обозначено. Денежные расходы и процент бюджета не вычислять без согласованного источника/правила. Не применять общий опубликованный rate limit как подтверждённую квоту аккаунта.

## 4. OData

До решения владельца не добавлять фактическую загрузку. Для варианта подготовки использовать существующие source='manual'/'onec' и external_id; аналитика независимо от способа поступления данных читает единый журнал. Зафиксировать будущие точки подключения и необходимые правила сопоставления менеджеров, уникальности, отмен/исправлений. Не показывать активную синхронизацию там, где её нет. Вариант реального подключения требует отдельного конкретного плана маппинга по фактическим метаданным 1С; не выполнять записи в 1С.

## 5. Проверки и выпуск

Проверки на временных SQLite/storage и синтетическом ключе: admin/manager/anonymous, агрегаты и границы дат, отмены/история/план, миграция на новой и прежней БД/повторный запуск, учёт DeepSeek и ошибки без утечки, сохранность старых сценариев. Провайдер/1С в тестах имитируются. Frontend affected tests + lint:ci + types + build; короткий E2E через npm run test:auth:e2e. Одно независимое ревью по риску, одна приёмка по брифу без повторного whole-review. Существующие обязательные проверки публикации остаются.

Commit/push/PR/merge разрешены owner policy после проверок; перед публикацией проверяются внешние триггеры. Рабочий сервер/БД не затрагиваются этой разработкой. Деплой только отдельной операцией после согласования точного main SHA/backup/rollback. Аддитивная схема позволяет откатить код без восстановления старой БД; доказать совместимость перед предложением выпуска.
