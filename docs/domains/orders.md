# Домен: счета, заказы и отправка в 1С

## 1. Что считается заказом в текущем проекте

Внутри приложения пользователь собирает локальный черновик счета, а затем отправляет его в 1С как заказ покупателя.

Цепочка выглядит так:

- пользователь набирает позиции в черновик на клиенте;
- черновик хранится в `localStorage`;
- при отправке backend создает локальный заказ в SQLite;
- затем заказ синхронизируется с 1С;
- только после успешной синхронизации выполняется списание локальных остатков по складам.

Важно:

- локальный заказ и заказ в 1С не создаются “одновременно в одной транзакции”;
- сначала создается локальная запись;
- потом идет попытка синхронизации в 1С;
- при ошибке локальный заказ остается в истории со статусом `error`.

## 2. Основные таблицы

### `orders`
Хранит шапку локального заказа:

- локальный номер;
- контрагент;
- договор;
- организация;
- дата;
- комментарий;
- статус;
- номер/дата/Ref_Key документа в 1С;
- итоговая сумма;
- сообщение об ошибке;
- автора заказа (`created_by_user_id`).

### `order_lines`
Хранит строки заказа:

- товар;
- склад строки;
- `warehouse_name_snapshot`;
- количество;
- цена;
- сумма.

### `stock_movements`
Используется для фиксации движений остатков, в том числе связанных с заказом.

## 4. Клиентская модель черновика

На frontend строка черновика хранится в типе `DraftLine`.

Ключевые поля:

- `itemId`
- `sku`
- `name`
- `categoryName`
- `price`
- `quantity`
- `available`
- `warehouseId`
- `warehouseName`
- `availableOnWarehouse`

Черновик сохраняется в `localStorage` через:

- `loadDraftLinesFromStorage`
- `saveDraftLinesToStorage`

Форма шапки счета отдельно сохраняется в `InvoiceFormState`.

## 5. Поток данных при отправке заказа

### Шаг 1. Подготовка на клиенте
Пользователь выбирает:

- контрагента;
- договор;
- организацию;
- дату;
- комментарий;
- строки черновика.

### Шаг 2. Валидация payload
В `stock_sync_api.py::_parse_order_payload` проверяются:

- корректный `counterpartyId`;
- опциональный `contractId`;
- дата;
- непустые строки;
- положительное количество;
- неотрицательная цена;
- корректный `warehouseId`.

### Шаг 3. Создание локального заказа
`stock_sync_web/service.py::create_and_sync_order`:

1. строит `bundle_lines`;
2. вызывает `db.create_order(...)`;
3. получает `order_id`;
4. загружает bundle заказа из БД.

### Шаг 4. Подготовка номенклатуры
`_ensure_order_items_ready`:

- проверяет, что у строк есть корректные ключи 1С;
- если товара нет в 1С, пытается найти или создать его;
- обновляет `onec_key`, `unit_key`, `unit_name` в локальной карточке.

### Шаг 5. Сборка payload в 1С
`_build_order_payload`:

- подставляет контрагента, договор, организацию;
- собирает табличную часть `Запасы`;
- рассчитывает НДС;
- валидирует остатки по выбранным складам;
- использует системные настройки 1С.

### Шаг 6. Синхронизация
Service вызывает:

- `client.create_sales_order(payload)`
- затем `client.get_sales_order(ref_key)`

### Шаг 7. Финализация
Если 1С вернула корректный `Ref_Key`, вызывается:

- `db.finalize_order_sync(...)`

В этот момент:

- заказ получает статус `posted_to_1c`;
- сохраняются `onec_ref_key`, `onec_number`, `onec_date`;
- выполняется локальное списание остатков по складам строк заказа.

### Ошибка
Если на любом шаге после `create_order` происходит исключение:

- вызывается `db.mark_order_error(order_id, str(exc))`;
- заказ остается в истории;
- статус становится `error`;
- локальное списание не выполняется.

## 6. Статусы заказа

Из текущей реализации видны как минимум:

- `posting_to_1c` - локальный заказ создан, идет попытка отправки;
- `posted_to_1c` - успешно отправлен и финализирован;
- `error` - ошибка при отправке или подготовке.

UI в истории заказов отображает их как:

- “В обработке”
- “Отправлен”
- “Ошибка”

## 7. Что показывается в UI

### Работа со счетом
- строки черновика;
- склад для каждой строки;
- доступный остаток на выбранном складе;
- цена, НДС, сумма;
- синхронизация справочников;
- тест доступа в 1С;
- отправка в 1С.

### История заказов
- локальный номер;
- дата;
- контрагент;
- список складов;
- статус;
- номер 1С;
- дата 1С;
- сумма;
- ошибка/заметка;
- кто создал заказ.

### Детали заказа
- табличная часть строк;
- склад каждой строки;
- количество, цена, сумма;
- контрагент, договор, организация, даты, комментарий;
- агрегаты по количеству и сумме.

## 8. Инварианты, которые нельзя нарушать

- заказ нельзя отправлять без строк;
- количество в строке должно быть больше нуля;
- цена в строке не должна быть отрицательной;
- каждая строка заказа должна быть привязана к конкретному складу;
- `warehouse_name_snapshot` должен сохраняться в строке;
- локальное списание нельзя делать до успешного ответа 1С;
- при ошибке отправки заказ должен оставаться в истории со статусом `error`;
- для связанных с 1С товаров нельзя терять `onec_key` и `unit_key`;
- проверка доступного остатка должна идти по конкретному складу строки, а не только по общему остатку.

## 10. Что обязательно проверять после изменений

### Команды
- `cd sm-techno-web && npm run build`
- `cd sm-techno-web && npm run lint`
- `cd sm-techno-web && npx tsc --noEmit`

### Ручные сценарии
- собрать черновик из нескольких строк;
- выбрать разные склады для разных строк;
- изменить количество в строке;
- убедиться, что нельзя превысить остаток выбранного склада;
- отправить заказ в 1С;
- проверить переход заказа в историю;
- открыть детали заказа;
- проверить склад каждой строки;
- проверить статус ошибки при искусственном сбое 1С;
- убедиться, что при ошибке остатки не списались;
- убедиться, что при успехе остатки списались именно по нужным складам.
