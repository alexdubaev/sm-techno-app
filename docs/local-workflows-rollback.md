# Локальный возврат: проверенный сценарий

Это инструкция для отдельной синтетической локальной копии; совместимость с VPS или старой production-базой не подтверждена. Не использовать сохранённую старую базу поверх новых записей. Архив `old-local-feature.bundle` содержит приватную историю и не публикуется.

Перед возвратом остановить только процессы своего экземпляра, исключить параллельные записи, сохранить согласованную копию текущей SQLite и storage и проверить её свежим `stock_sync_web.vps_integrity.validate_database_storage_pair` из нового кода. `scripts/vps_backup.py` создаёт проверяемый архив, а `scripts/vps_restore.py --verify-only` проверяет его; восстановление выполняется только в пустой каталог. Копия и хэши файлов и строк проверяются до запуска старого кода. Не трогать пользовательские данные, исходный экземпляр и настройки 1С.

В репетиции 30 октября 2026 новый backend записал синтетические клиент, КП, договор, спецификацию и источники. Старый код `8f96c36be402b4651d5df4681fd130169689945b` был запущен на отдельной копии текущих данных, прочитал остаток, клиента, КП и оба документа. Новый verifier подтвердил данные и client asset keys после чтения; сверены строки бизнес-таблиц и хэши файлов. Отдельное восстановление проверенного архива в пустой каталог сохранило SQL dump и 12 хэшей файлов; время backup, verify и restore 0,875 с для этой небольшой синтетической выборки, без времени переключения сервиса. Замер не является оценкой для рабочего объёма.

Для этого Windows fixture строки старых файловых путей относительны рабочему каталогу. Проверочная копия storage содержит как исходные `documents/` и `commercial_offers/`, так и их точное зеркальное расположение `.local-demo/candidate-data/`, чтобы одновременно проверить legacy пути и asset keys без изменения строк БД. Перед применением к другому экземпляру необходимо проверить его фактические пути и непротиворечивую схему хранения; нельзя считать эту раскладку универсальной.

Архивы и машинное evidence репетиции находятся в `D:/codex-local-workflows-check-20261030/.local-demo/rehearsal/`. Исходный fallback bundle: `C:/Users/Alexandr/.codex/artifacts/local-document-workflows-20261030/old-local-feature.bundle`. Старый действующий локальный экземпляр не изменялся. Для реального переключения дополнительно нужны подтверждённые целевой контур, согласованный backup, проверенные путь и порядок восстановления; эта репетиция сама по себе не разрешает deploy.

Проверенная совместимость относительных путей для **этой** копии: текущий код сохранил `documents.output_path` и `commercial_offers.output_path` относительно рабочего каталога, начиная с `.local-demo/candidate-data/`; при этом verifier ищет opaque `client_document_assets.storage_key` под `storage/documents/client_assets/`. Поэтому в новом пустом staging-каталоге скопированы все папки `documents` и `commercial_offers` из остановленного текущего synthetic storage в `storage/`, а затем эти же папки скопированы в `storage/.local-demo/candidate-data/`. SQLite snapshot получен API `sqlite3.Connection.backup`, строки не переписывались. Новый verifier проверил обе группы ссылок в этой структуре, затем стандартный backup/verify/empty restore и сравнение хэшей прошли. Эти дополнительные папки — только layout проверочного staging; они не подменяют или редактируют бизнес-данные, исходное storage осталось нетронутым.

Для старого кода была отдельно скопирована **вся текущая** остановленная synthetic data-папка в пустой `<old-code>/.local-demo/candidate-data/`; старый процесс запускался с рабочим каталогом `<old-code>` и указывал на эту копию. В этом расположении записанные relative paths снова указывают на те же байты, а клиентские assets доступны по storage root. После остановки старого процесса новый verifier был запущен повторно на отдельном staging с тем же зеркальным layout; business rows и хэши файлов сверены с текущим экземпляром. Выполненные команды доступны в локальных воспроизводимых helper-файлах `D:/codex-local-workflows-check-20261030/.local-demo/rehearse.py`, `old-server.py`, `old-readback.py`, `old-integrity.py`; перед применением к другим путям их нужно адаптировать и проверить, а не запускать на рабочих данных вслепую.

Foreground launcher всегда задаёт собственным дочерним процессам `TEMP`, `TMP` и `TMPDIR` равными `D:/codex-local-workflows-test-temp-20261030`, вне исходного дерева; он проверяет, что каталог не вложен в source или текущий рабочий каталог. Это локальные переменные процесса, а не изменение системных настроек. Запускать из каталога исходной копии или другого каталога, который не является родителем указанного временного пути.
