# СМ ТЕХНО: изолированный тестовый деплой на VPS

## Цель

Развернуть на VPS независимый тестовый экземпляр СМ ТЕХНО, используя
установленный Docker. Он не должен использовать, менять или упоминать в
исходном коде и конфигурации проекта существующие на VPS контейнеры, их
сети либо конфигурацию reverse proxy. Sites остаётся включённым. DNS и
публичный HTTPS не входят в эту итерацию.

## Границы

В этой ветке создаётся отдельный Compose-проект `sm-techno-test` с
контейнерами frontend и backend. У него собственная внутренняя сеть и
отдельные host-каталоги:

- `/srv/sm-techno-test/data` — SQLite-база;
- `/srv/sm-techno-test/storage` — generated files и uploads;
- `/srv/sm-techno-test/backups` — резервные копии.

Frontend публикуется только как `127.0.0.1:3000`, backend — только как
`127.0.0.1:8000`. Доступ для проверки будет организован SSH-туннелем. Ни
один сервис СМ ТЕХНО не подключается к существующим Docker-сетям и не
занимает внешние порты VPS.

## Приложение

### Персистентные данные

`SM_TECHNO_DB_PATH` переопределяет путь к SQLite, а
`SM_TECHNO_STORAGE_ROOT` — корень generated files. Если переменные не
заданы, Windows-запуск продолжает использовать прежние пути внутри
рабочего дерева. База, storage и backup-архивы не включаются в Docker
images и не попадают в Git.

Для переноса создаётся отдельная утилита. Она делает online SQLite backup,
проверяет `PRAGMA integrity_check`, очищает в копии `users.onec_password`
и `app_sessions`, затем копирует storage. Исходная база и storage только
читаются. Переносятся все деловые данные, настройки и пользователи.
Пользовательские пароли приложения остаются (как уже хранимые хэши), но
пользователи заново входят в приложение и повторно вводят пароль 1С.

### Пароли 1С

Windows DPAPI значения сохраняют формат `dpapi:` и прежнее поведение. На
Linux новые значения должны иметь формат `fernet:` и шифруются ключом из
`SM_TECHNO_CREDENTIAL_KEY`. Ключ хранится только в VPS `.env`. Если ключ
отсутствует, Linux не может записать plaintext-пароль 1С и возвращает
безопасную диагностическую ошибку. Нерасшифровываемые `dpapi:` значения
на Linux не считаются действительными учётными данными.

### Frontend

Frontend переводится с Vinext/Sites/Cloudflare runtime на обычный Next.js
Node runtime: `next build` с `output: "standalone"` и `next start`.
Клиент продолжает обращаться только к относительным `/api/*`. Существующий
route handler остаётся server-side fallback для локальной разработки с
`BACKEND_API_BASE_URL`; в контейнерном тестовом контуре frontend также
может проксировать к backend по внутренней Docker-сети.

## Контейнеры и эксплуатация

В репозитории появляются backend и frontend Dockerfile, Compose-файл,
`.dockerignore`, `.env.example` и команды backup/restore. Образы не
содержат SQLite, storage, секреты и backup-архивы. Backend получает
read-only assets/templates из образа и write-доступ только к примонтированным
data/storage. Для SQLite используется один Uvicorn worker.

Контейнеры имеют healthchecks, `restart: unless-stopped` и запускаются
изолированно. Compose не определяет external network и не содержит имён,
связанных с другими проектами VPS.

## Приёмка тестового деплоя

После локальных тестов и сборок копия данных переносится в
`/srv/sm-techno-test`, где запускается только `sm-techno-test`. Проверки:

1. frontend и backend проходят healthcheck;
2. через SSH-туннель открывается UI, выполняется вход прежними учётными
   данными приложения и доступны перенесённые данные;
3. тестовая локальная операция сохраняется после перезапуска контейнеров;
4. backup и restore проходят на тестовой копии;
5. проверка 1С ограничена read-only запросом справочника; создание
   контрагентов и заказов запрещено.

Эта итерация не включает DNS, Caddy, TLS, доступ по публичному домену,
слияние в `main`, отключение Sites или изменение существующих сервисов VPS.
Для будущего публичного запуска потребуется отдельное согласованное
решение об edge proxy или выделенном публичном IP; оно не является частью
данной реализации.

## Тесты

До реализации добавляются тесты на разрешение путей, Fernet и отсутствие
plaintext на Linux, sanitised online-copy базы и storage, а также проверки
Node build и Compose-конфигурации. Регрессионные Python-тесты, frontend
typecheck/lint и production build выполняются перед деплоем.
