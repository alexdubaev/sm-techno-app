# CRM: сотрудники в работе в общей вкладке «Клиенты 1С»

## Цель

Сделать существующие активные назначения CRM видимыми всем пользователям в системной вкладке «Клиенты 1С», не меняя модель назначений, права и синхронизацию с 1С.

## Границы

- Изменение касается только выдачи и отображения системной primary-вкладки «Клиенты 1С».
- Источник истины — существующие активные строки `crm_assignments`: `archived_at IS NULL`.
- Один клиент может иметь несколько активных назначений у разных пользователей; это не ограничивается и не меняется.
- Не создаются таблицы, поля клиента, endpoint'ы или сущности ответственных.
- Названия личных вкладок других сотрудников, их логины, пароли, email и данные 1С не передаются и не показываются.
- Персональные вкладки не получают постоянный визуальный статус владельцев.
- Функция не пишет в 1С и не запускает CRM/1С-синхронизацию.

## Backend и API

`GET /api/crm/clients` при `primaryOnly=true` расширяет каждую сериализованную карточку обязательным полем:

```json
"workOwners": [
  { "userId": 4, "fullName": "Иван Петров" }
]
```

Для свободного клиента возвращается `"workOwners": []`. В элементе допускаются только `userId` и `fullName`; `username` намеренно не выбирается и не передаётся. Если `users.full_name` пуст, API передаёт пустую строку, а UI отображает нейтральное «Имя сотрудника не указано».

Repository получает метод `list_active_work_owners_for_client_ids(client_ids)`. Внутренние SQL-псевдонимы сразу нормализуются repository/API-слоем к единому публичному контракту `userId` / `fullName`; `id` и `full_name` не выходят в API, TypeScript, frontend-код, тесты или документацию. Метод возвращает активные назначения для всего списка одним SQL-запросом:

```sql
SELECT a.crm_client_id, u.id AS user_id, u.full_name
FROM crm_assignments AS a
JOIN users AS u ON u.id = a.owner_user_id
WHERE a.crm_client_id IN (...)
  AND a.archived_at IS NULL
ORDER BY a.crm_client_id, u.full_name, u.id
```

API получает первичный список карточек, передаёт его ID в этот метод один раз, группирует строки по ID карточки и добавляет массив к сериализации. Поэтому количество запросов за владельцами не зависит от числа карточек и N+1 не появляется. Доступ к primary-вкладке сохраняет текущую авторизацию; сведения о сотруднике из `full_name` видны каждому пользователю, который уже может открыть этот общий список.

Перемещение одного сотрудника между его личными вкладками меняет только `tab_id` назначения и не влияет на owner-список. Архивирование или удаление назначения исключает владельца из следующего server-side ответа, так как выбираются только строки с `archived_at IS NULL`.

## Frontend и кэш

В `sm-techno-web/lib/types.ts` добавляются обязательные типы:

```ts
export type CrmWorkOwner = {
  userId: number;
  fullName: string;
};

// CrmWorkspaceClient
workOwners: CrmWorkOwner[];
```

Ответ primary-list поступает через существующий поток workspace и сохраняется текущим `crm-workspace-cache` вместе с полными объектами карточек. Дополнительной схемы кэша и отдельных клиентских источников истины не требуется.

После успешного `moveCrmClient`, совершённого из «Клиентов 1С», workspace обязательно повторно загружает primary-list с backend и заменяет его в состоянии и `crm-workspace-cache`. Следовательно, пользователь, который взял клиента в работу, сразу видит своё настоящее имя без ручного обновления. Остальные пользователи получают актуальные данные при существующем фоне обновления, ручном обновлении, повторном открытии CRM или перезагрузке; real-time транспорт не добавляется.

## Представление

Desktop-таблица primary-вкладки получает отдельную колонку «В работе»:

- `Свободен`, если `workOwners` пуст;
- одно настоящее имя при одном владельце;
- два имени через запятую при двух владельцах;
- первое имя и `+N` при трёх и более владельцах.

Для трёх и более сотрудников нажатие на статус или `+N` открывает небольшой доступный popover с полным списком имён. Tooltip может дублировать сведения, но не является единственным способом увидеть остальных сотрудников.

Mobile-карточка primary-вкладки получает самостоятельный, визуально вторичный информационный блок между реквизитами компании и контактными действиями:

- `В работе: Иван Петров` для одного или двух коротких имён;
- на узких экранах или при трёх и более владельцах — `В работе у N сотрудников` с раскрываемым полным списком;
- `Свободен`, если владельцев нет.

Длинные имена переносятся внутри блока и не расширяют карточку за пределы viewport. Компоненты получают явный признак primary-вкладки, чтобы в личных вкладках статус не рендерился.

## Тестирование

Backend-покрытие проверяет API primary-list и repository:

1. Свободный клиент возвращает пустой массив.
2. Один и несколько активных сотрудников возвращаются всем допустимым пользователям только с `userId` и `fullName`.
3. Перемещение назначения между личными вкладками сохраняет владельца.
4. Архивация и удаление исключают владельца.
5. При отличающихся `username` и `full_name` возвращается только настоящее имя; при пустом `full_name` логин не становится fallback.
6. Пакетный путь делает один запрос владельцев для полного списка, включая большой набор ID.

Frontend-покрытие проверяет desktop и mobile primary-представления для свободного, одного, двух и нескольких владельцев, click-popover полного списка на desktop, длинные имена, нейтральную подпись пустого имени, отсутствие отображения на личных вкладках и сохранение свежих `workOwners` в кэше после немедленного обновления primary-list после `moveCrmClient`.

## Вне области задачи

- Ограничение «один клиент — один менеджер».
- Редактирование или удаление чужих назначений.
- Новые права, WebSocket, уведомления и миграции данных.
- Любые изменения 1С, `move_client`, структуры `crm_assignments`, порядка и цветов карточек.
