# Безопасная отправка заказов в 1С

## Цель

Исключить повторное создание удалённого заказа и повторное списание склада при сбоях между локальной SQLite и 1С.

## Границы

Изменяется только контур заказов: SQLite-репозиторий, сервис отправки, OneC-клиент, API восстановления и UI карточки заказа. Существующие CRM-изменения и их данные не меняются.

## Состояния

`orders.status` использует следующие значения для новых и мигрированных заказов:

- `reserved` — строки заказа и резерв остатков сохранены; POST ещё не начинался;
- `sending_to_1c` — запрос передан transport layer, поэтому его результат нельзя считать отрицательным;
- `remote_created_pending_finalize` — Ref_Key записан, но склад ещё не финализирован;
- `posted_to_1c` — remote order подтверждён и резерв конвертирован в одно фактическое списание;
- `error_before_remote_write` — ошибка произошла до попытки POST, резерв освобождён;
- `remote_state_unknown` — connection/transport error после начала POST, новый POST запрещён;
- `written_off_locally` — legacy ручное списание, разрешённое только для заказов без remote-неопределённости.

Старые значения `posting_to_1c` и `error` сохраняют совместимость в отображении, но новые операции их не создают. При запуске миграции старый `posting_to_1c` переводится в `remote_state_unknown`, так как достоверно установить, дошёл ли прежний POST до 1С, невозможно; старый `error` переводится в `error_before_remote_write` только при пустом `onec_ref_key`, иначе — в `remote_created_pending_finalize`.

## Данные и инварианты

Таблица `order_reservations` хранит `(order_id, item_id, warehouse_id, quantity)` с уникальным ключом на пару заказа и склада. `orders` получает `sync_attempt_key` (UUID) и поля времени попытки. В доступный остаток включается физический баланс за вычетом всех активных резервов.

Создание заказа и резерва выполняется через SQLite `BEGIN IMMEDIATE`: строки предварительно агрегируются по `(item_id, warehouse_id)`, затем проверяется доступный баланс, вставляются заказ, строки и резервы. Поэтому одновременно отправленные заказы не могут зарезервировать одну последнюю единицу дважды.

`stock_movements` получает уникальный partial index для фактических движений `out` одного `(order_id, item_id, warehouse_id)`. Финализация допускает повторный вызов: при наличии движения она не меняет баланс второй раз и приводит заказ к `posted_to_1c`.

## Отправка и reconciliation

Перед POST сервис записывает `sending_to_1c`. В поле `Комментарий` 1С добавляется неизменяемый marker вида `[SMT:<sync_attempt_key>]`, сохраняя пользовательский комментарий.

Если `create_sales_order` вернул `Ref_Key`, он сохраняется отдельной локальной транзакцией до GET. После GET сервис переводит заказ в `remote_created_pending_finalize`, затем выполняет идемпотентную финализацию.

Если transport error возникает после начала POST, сервис сохраняет `remote_state_unknown`, оставляет резерв и не повторяет POST. Администратор вызывает recovery. Recovery использует сохранённый Ref_Key либо точный marker, если OneC OData поддерживает фильтрацию по `Комментарий`; найденный remote order локально фиксируется и финализируется. Если поиск недоступен или не дал однозначного результата, состояние не меняется и UI сообщает о необходимости ручной сверки. Recovery никогда не создаёт новый order в 1С.

## Доступ и интерфейс

Recovery endpoint доступен только admin. Ручное списание отклоняется для `sending_to_1c`, `remote_created_pending_finalize` и `remote_state_unknown` с сообщением о необходимости сверки с 1С. В карточке этих состояний admin видит действие «Проверить состояние в 1С / продолжить финализацию»; для остальных пользователей это действие скрыто.

## Ошибки

Ошибка до отправки освобождает reservation и сохраняет `error_before_remote_write`. Ошибка после Ref_Key не стирает Ref_Key. Ошибка финализации не меняет remote identity и оставляет `remote_created_pending_finalize`; повтор recovery безопасен.

## Проверки

Тесты используют fake OneCClient с управляемыми сбоями: до POST, после remote creation без ответа, после Ref_Key перед GET, при финализации и при повторном recovery. Они также проверяют атомарность резерва при конкуренции, идемпотентное списание и запрет ручного списания uncertain states.
