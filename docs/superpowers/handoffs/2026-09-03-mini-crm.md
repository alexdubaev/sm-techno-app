## 3. Что пользователь решил

- CRM — отдельный нативный раздел приложения, предполагаемый маршрут `/crm`. Существующий раздел `/clients` и потребителей его API сохранить совместимыми.
- Relatio: `https://github.com/charbelkassab/relatio-crm` — только ориентир по взаимодействию. Express, PostgreSQL, отдельную авторизацию, MCP, почтовый модуль и самостоятельный UI не переносить. Решение о повторном использовании конкретных исходников не принималось.
- «Организация» — компания покупателя. «Имя клиента» — контактное лицо. У компании может быть несколько личных контактов у каждого менеджера.
- Основные столбцы: организация, имя клиента, город, почта, сайт, телефон, комментарии, дата звонка, напоминание позвонить.
- Главная «Клиенты 1С» всегда показывает связанные компании. «В работе» — постоянная личная вкладка. Остальные вкладки пользователь создаёт сам.
- У пользователя одна текущая личная вкладка на компанию. У другого менеджера назначение может отличаться. Название личной вкладки показывается меткой в главном списке. Перемещение не убирает связанного клиента из главного списка.
- Локальные потенциальные клиенты без ИНН разрешены. Они не отправляются в 1С автоматически, даже после заполнения реквизитов: требуется явное действие пользователя. После связывания реквизиты компании обновляются в обе стороны.
- При совпадении по ИНН/КПП предлагать связать; при конфликте одного реквизита в двух системах показывать оба значения. Не выбирать победителя по времени без участия человека.
- Контактные лица, их телефоны/почта, комментарии, история звонков, напоминания, вкладки, порядок и цвета в 1С не передаются.
- История и личные данные доступны владельцу и администратору. Администратор выбирает сотрудника в шапке CRM и видит его пространство, включая выключенные аккаунты.
- Все сотрудники добавляют клиентов, редактируют и перемещают их в своём пространстве. Только администратор удаляет/архивирует клиента или полностью снимает его личное назначение, включая «Оставить только в основной».
- Запрет удаления относится к клиентам. Удаление произвольной вкладки допускается с обязательным переносом всех её клиентов в другую личную вкладку; это не должно обходить запрет удаления. Постоянные вкладки удалить/переименовать нельзя.
- Напоминания нужны только в открытом приложении и при следующем входе. Телефония, аудиозаписи и push при закрытом приложении не нужны.
- Drag-and-drop меняет положение всей строки между соседями. Режим «Мой порядок» сохраняется для пользователя и вкладки; при поиске/фильтрах или другой сортировке перенос отключён.
- Палитра — 12 цветов плюс сброс. Цвет и порядок сохраняются на сервере, доступны с другого устройства и не меняют данные другого пользователя.
- Excel: вся доступная клиентская база или все клиенты текущей вкладки. Листы «Клиенты» и «Контакты», личные метки, порядок и цвета; не выгрузка секретов/внутренней БД и не всей истории общения. Поиск/временные фильтры не урезают экспорт вкладки.

Все детали удаления, восстановления, уведомлений, меню и выгрузки изложены в полном плане. Не возвращаться к прежней идее синхронизации комментариев или автоматической отправки каждого нового лида в 1С.

## 4. Подтверждённое устройство приложения

### Frontend

Источники находятся в `sm-techno-web/`. Фактический `package.json` использует React 19, TypeScript, Tailwind 4, `vinext`, Vite, Cloudflare и Sites. Скрипты: `dev = vinext dev`, `build = vinext build`, `lint = oxlint`, `start = wrangler dev --config dist/server/wrangler.json`. Требование Node — не ниже `22.13.0`.

В папке есть `.openai/hosting.json`, `vite.config.ts` и `components.json`. При реализации учитывать соответствующие навыки Sites и компонентного стека, если они доступны в окружении нового агента. Наличие hosting-конфигурации не означает разрешение опубликовать проект. Не заменять действующий стек обычным Next CLI по старым инструкциям.

Точки входа:

| Путь | Что уже делает и зачем читать |
| --- | --- |
| `sm-techno-web/components/app-shell.tsx` | Навигация, меню по ролям; добавить пункт CRM и общий показ личных напоминаний |
| `sm-techno-web/app/clients/page.tsx` | Существующая карточка создания, список, ручная синхронизация, повтор отправки; изучить ради совместимости |
| `sm-techno-web/components/resizable-table.tsx` | Существующие изменяемые ширины столбцов; согласовать с drag-and-drop строк |
| `sm-techno-web/components/auth-provider.tsx` | Сессия и `isAdmin`; административный просмотр не подменяет сессию |
| `sm-techno-web/lib/api.ts` | Авторизация, таймаут 15 секунд, повторы GET, браузерный GET-кэш по URL, сброс кэша после мутаций |
| `sm-techno-web/lib/types.ts` | `CrmClient`, `AppUser`, существующие контракты документов и клиентов |
| `sm-techno-web/app/api/[...path]/route.ts` | Прокси `/api/*` в FastAPI через `BACKEND_API_BASE_URL`; передача authorization и тела/ответа, включая скачивание XLSX |

Список CRM, кэш и запросы должны включать контекст просматриваемого сотрудника. При переключении отменять старые запросы; запоздалый ответ нельзя сохранять в новом контексте. Версии CRM-записей предпочтительно передавать явно в JSON: нынешний прокси пропускает только ограниченный набор заголовков запроса.

### Backend и БД

| Путь | Проверенное поведение |
| --- | --- |
| `stock_sync_api.py` | FastAPI, пользовательская/административная авторизация; `/api/clients`, создание, `send-to-onec`, `/api/references/sync`; при импорте создаёт глобальный `SERVICE` и запускает bootstrap |
| `stock_sync_web/service.py` | Работа с клиентами и документами; `create_client` сейчас требует полноценные реквизиты и пытается создать контрагента в 1С; `sync_counterparties` обновляет справочник и CRM-карточки |
| `stock_sync_web/database.py` | `crm_clients`, users/sessions, миграции; CRM-клиенты пока не имеют личного владельца; импорт перезаписывает ряд полей, включая `notes`, `contact_person`, email/phone |
| `stock_sync_desktop/database.py` | Базовые таблицы и подключение SQLite; путь по умолчанию — `stock_sync.db` рядом с исходниками данного checkout |
| `stock_sync_desktop/onec_api.py` | Действующий OData-клиент; metadata, список/создание/обновление контрагентов, контактная информация, поиск по ИНН, HTTP PATCH |
| `requirements.txt` | FastAPI, openpyxl, pandas, uvicorn, docxtpl и прочие текущие зависимости |

Связь существующих записей: `crm_clients.linked_counterparty_id → counterparties.id → counterparties.onec_key / Ref_Key`. API использует смесь `source: local/onec`, `id`, `crmClientId`, `counterpartyId`. Нельзя считать `source === local` признаком отсутствия связи с 1С: синхронизированная CRM-карточка тоже может приходить как `local`. Проверять фактическую связь.

Методы создания клиентов сейчас проверяют дубли глобально по ИНН, а чтение списка не ограничивает клиентов новым владельцем. Простого добавления визуальной фильтрации в React недостаточно. В новых личных клиентах проверка дублей должна учитывать область доступа; нельзя раскрывать имя/телефон чужого локального лида через текст ошибки. Независимые личные лиды разных сотрудников не объединять без связывания с общей компанией.

Пароли 1С в текущем коде защищаются Windows DPAPI. Новый worktree, другая Windows-учётная запись или будущий Linux-хост не гарантируют возможность их расшифровать. Не переносить секреты в Markdown, клиентский код, XLSX, логи или новую открытую таблицу. Для серверной очереди использовать действующий механизм учётных данных автора; при его недоступности сохранять понятную ошибку и очередь.

## 5. Границы модулей и порядок реализации

### Этап A. Подготовка и безопасный baseline

- Проверить ветку и документы, подготовить зависимости worktree по актуальным манифестам.
- Запустить релевантные существующие проверки до изменения кода и записать результат. Различать ошибки окружения и регрессии.
- Проверить источник настроек локального запуска. В worktree не копировались `.env.local`, рабочая база, учётные записи или runtime-хранилища.
- Для разработки использовать отдельную тестовую SQLite и фальшивый клиент 1С. Не запускать автоматические миграции на рабочей базе ради теста.

### Этап B. Модель и доступ

- Дополнить общую карточку компании и создать отдельное личное пространство «сотрудник + компания», не смешивая его с `Ref_Key` 1С. Личная история должна существовать и после снятия назначения вкладки.
- Отдельные сущности: системные/пользовательские вкладки, личное назначение, контакты, события, напоминания, настройки строк, журнал административных действий, состояние/очередь обмена.
- Уникальность: одна «В работе» на пользователя, не более одного активного личного назначения компании на пользователя, одна общая связь с конкретным контрагентом 1С. Порядок/цвет отдельно на пользователя, вкладку и компанию.
- Поддержать старые строки и документы миграцией без потери идентификаторов. Старых локальных клиентов без владельца отдавать в административное распределение; связанные компании остаются общими. Старые заметки не превращать в личные комментарии без автора.
- Закрыть старые и новые пути чтения/изменения/экспорта, через которые могли бы утечь личные данные. Политика ролей реализуется в общем серверном слое.
- Новую логику выделять в небольшие CRM-модули и FastAPI router; не расширять бесконтрольно монолитные `service.py` и `stock_sync_api.py`. Для точек совместимости оставить вызовы существующих сервисов.

### Этап C. Базовый интерфейс

- Добавить `/crm` в действующую оболочку с двумя постоянными вкладками и личными пользовательскими вкладками.
- Реализовать локальное создание, карточку с общими реквизитами и личными контактами, таблицу, поиск, меню, перемещения и метки. Основной список не скрывает связанную компанию при личном назначении.
- Добавить административный переключатель сотрудника и чёткое отображение контекста. В чужом пространстве не включать обычные управляющие действия владельца просто потому, что пользователь — администратор; доступны оговорённые административные действия.
- Реквизиты компании и данные личного контакта должны редактироваться в разных явно подписанных областях. В строке/Excel использовать правило основного контакта из плана.

### Этап D. Общение и удаление

- Реализовать личную историю звонков/комментариев с автором и временем, исправления с сохранением истории.
- Реализовать напоминания, перенос/завершение/отмену, просроченные и общий индикатор в оболочке. Административный просмотр не изменяет статусы чужих напоминаний.
- Реализовать обратимое удаление только администратором, с причиной и журналом реального исполнителя. Различать личное исключение связанной компании и архив локальной компании.
- Изменение назначения на `null`, архив или удаление контейнера не должны обходить проверку роли. Удаление пользовательской вкладки переносит все строки атомарно.
- Не восстанавливать административно архивированное назначение неявно через обычное «Добавить»: показывать состояние архива и необходимость восстановления администратором. Существующая личная история сохраняется.

### Этап E. Порядок, палитра и Excel

- Реализовать drag-and-drop с линией вставки, отменой, автопрокруткой и клавиатурными «Выше/Ниже». Отделить его от выделения текста, ссылок и изменения ширины колонок.
- Сервер принимает клиента и соседей вставки, проверяет область/версию и сохраняет порядок транзакционно. Не использовать визуальный индекс строки как идентификатор. При ошибке откатывать оптимистическое изменение.
- Сохранять один из 12 ключей цвета или `null`. Личные цвета основной и рабочей вкладок независимы; перенос между личными вкладками сохраняет цвет.
- Генерировать Excel через openpyxl на сервере с двумя листами согласно плану. Учитывать все страницы списка, порядок и цвета, дедупликацию связанных компаний и контекст администратора. Не включать архивные личные записи и их контакты в активную выгрузку; общая связанная компания сама по себе остаётся доступной в основном списке.

### Этап F. Обмен с 1С

- Добавить явное создание/связывание для выбранного локального клиента с проверкой обязательных реквизитов только на этом шаге. Старое мгновенное создание из `/clients` не использовать как реализацию сохранения нового локального лида.
- При связывании с уже общей компанией сохранять личную историю и все старые ссылки документов. Не объединять чужую личную историю. Для идентичностей, на которые уже ссылаются документы, использовать устойчивую связь/сопоставление, не удаление и пересоздание.
- Разделить входящий импорт общих полей и личные поля CRM; старый массовый upsert не должен затирать незавершённую локальную правку или новую личную историю.
- Реализовать persistent-очередь исходящих изменений, версии, последнее согласованное состояние и конфликты по полям. Сохранять намерение отправки и локальную правку одной транзакцией; перезапуск не теряет задание.
- Не отправлять изменения от выключенного автора или с недействующими credentials. Не считать результат отправки успешным без подтверждения; не повторять POST создания автоматически после неизвестного результата.
- Сеть не держит транзакцию SQLite открытой. UI получает сохранённую карточку и статус очереди быстро: существующий клиентский таймаут 15 секунд короче 60-секундного таймаута одного запроса OData.
- Входящий обмен запускать по оговорённой активности пользователя и ручной кнопке; не заводить второй неконтролируемый процесс синхронизации в каждой вкладке браузера. Исходящая очередь — серверная, с защищённым захватом заданий против двойной обработки.
- На заглушках полностью проверить логику до пробной записи в реальную 1С.

## 6. Что требуется проверить по действующей 1С

Это неизвестные факты окружения, а не открытые продуктовые решения:

| Проверка | Почему нужна / как поступать |
| --- | --- |
| Фактические поля города и сайта | В текущем адаптере нет готового общего двустороннего отображения этих новых полей. Прочитать metadata; неподдерживаемое поле остаётся CRM-only с явной отметкой |
| Поддержка условной записи версии | Текущий `_request_raw` не реализует контроль ETag/If-Match. Проверить возможности публикации, не предполагать их. Без безопасной условной записи не включать автоматический PATCH изменений |
| Права конкретного пользователя 1С | Доступ на чтение не доказывает доступ на создание/изменение; проверить на оговорённом тестовом контрагенте |
| Контактная информация компании | При изменении общего телефона/почты сохранить другие элементы табличной части 1С; не перезаписывать её урезанным массивом и не включать личные CRM-контакты |
| Частичный успех создания | Имеющийся `OneCCounterpartySyncError` содержит созданного контрагента. Сохранить связь и продолжить недостающую часть, не создавать новый объект |

Не копировать реальные секреты или данные клиентов в handoff. Сначала read-only диагностика, затем только согласованная тестовая запись. Не изменять конфигурацию 1С автоматически ради появления отсутствующих полей.

### Минимальный сквозной сценарий приёмки

1. Пользователь А создаёт локальную компанию без ИНН в «В работе», добавляет два контакта, комментарий и напоминание.
2. Перетаскивает строку, выбирает цвет, обновляет страницу — данные и оформление сохраняются.
3. Создаёт «Отказ», переносит компанию; личная история сохраняется. До связывания компания не появляется в главном списке.
4. Через fake-1С связывает компанию с контрагентом; в главном списке появляется метка «Отказ». Возвращает в «В работе» — метка обновляется, главный порядок/цвет не меняются.
5. Пользователь Б видит общую компанию, но не личные записи А, и создаёт своё назначение и контакты. Проверить это прямыми API-запросами и экспортом.
6. А не может удалить/архивировать клиента или снять назначение. Администратор выбирает CRM А, проверяет данные, архивирует и восстанавливает; CRM Б и документы остаются целыми.
7. Экспорт всей базы и вкладки открывается корректно, содержит все нужные строки, контакты, цвета и личные метки, без данных Б в выгрузке А.
8. После пропуска срока появляется напоминание. Чужой административный просмотр не меняет его состояние.
9. Сетевая ошибка, перезапуск, частичный успех POST и конфликт одновременных правок воспроизводятся на заглушках без дублей и потери локальных данных.
