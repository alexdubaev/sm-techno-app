## Что реализовано

### CRM API и данные

- Личные постоянные/пользовательские вкладки, назначения, контакты, история,
  напоминания, аудит, ручный порядок и палитра строк.
- Ролевая изоляция: пользователь не получает чужую CRM; администратор обязан
  передавать явный `ownerId`.
- Локальные лиды создаются во вкладке «В работе», архивируются и
  восстанавливаются только администратором; архив не затрагивает 1С.
- Карточки имеют оптимистичную версию. `PATCH /api/crm/clients/{id}` требует
  `expectedVersion` и возвращает 409 при устаревшей правке.
- Связанные с 1С карточки используют durable outbox `crm_sync_jobs`; разные
  локальные изменения сворачиваются в pending-задачу. Новая правка во время
  running-задачи создаёт новую pending-задачу, а старое завершение не затирает
  её статус.
- Автоматическая запись в 1С намеренно блокируется статусом
  `blocked_capability`, пока OData не подтвердит безопасную условную запись
  (ETag/If-Match). Это предохранитель, не временная ошибка.
- Импорт 1С не перезаписывает карточки со статусом `pending` или
  `blocked_capability`.
- Явная отправка локального лида в 1С доступна через
  `POST /api/crm/clients/{id}/send-to-onec`; сначала валидируются ИНН/КПП,
  затем переиспользуется существующий транспорт.
- Реализованы поиск/подтверждение существующей связи, очередь создания и
  безопасные повторы; последние коммиты дополнительно защищают архивированные
  лиды от постановки/повтора/связывания 1С-задач.

### Excel

- `stock_sync_web/crm_export.py` создаёт `.xlsx` с листами «Клиенты» и
  «Контакты», фильтрами, закреплённой шапкой, переносом комментариев,
  форматом текста для ИНН/КПП/телефонов, защитой от Excel-формул и цветов.
- `GET /api/crm/export?scope=all|tab&tabId=...` серверно проверяет область
  владельца и отдаёт только доступные данные.

### Интерфейс

- Раздел `/crm` подключён к app shell.
- Есть вкладки, поиск/фильтр синхронизации, карточки/таблица, создание лидов,
  перенос, палитра, восстановление сохранённого цвета, экспорт Excel.
- Детальная карточка содержит личные контакты, историю и напоминания.
- Администратор видит явный selector сотрудника; выбранный `ownerId` проходит
  через список, создание, перемещение, цвет, экспорт и detail-операции.

## Риски и следующий порядок работы

1. Провести целевой code review последних 1С-операций: юридическое лицо должно
   совпадать по ИНН+КПП, ИП — по ИНН; обрыв после POST не должен создать дубль.
   Использовать fake `OneCClient`, не настоящую 1С.
2. Довести `crm_sync_jobs` до полного worker lifecycle: атомарный claim,
   экспоненциальный retry сетевых ошибок, blocked для прав/реквизитов,
   защита авторскими credentials, restart-safe обработка. Проверить гонки
   отдельными тестами.
3. Добавить field-level conflict store/resolve для одновременной remote/local
   правки. Не включать автоматические remote update до capability probe OData.
4. Исправить оставшийся UX-разрыв создания: поля контактного лица и комментария
   в форме нового лида должны создавать owner-scoped CRM contact/event, а не
   становиться общими реквизитами карточки. Сохранить fallback компании для
   отображения/экспорта.
5. Реализовать контекстные административные archive/restore/«оставить только
   в основной» с чётким подтверждением области воздействия и visible audit.
6. Проверить DnD/ручной порядок и цвета основной вкладки: изменение цвета не
   должно сбрасывать `position`; основная 1С-вкладка требует отдельного
   представления предпочтений согласно плану.
7. Финальная проверка: полный Python набор, frontend Node-тесты, затем
   `npm run lint`, `npx tsc --noEmit`, `npm run build`. Если окружение всё ещё
   неполное, зафиксировать конкретный недостающий бинарник/пакет; не удалять
   `node_modules` и виртуальное окружение без разрешения.
