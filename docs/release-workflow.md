# Release Workflow

## Назначение веток

- `main` - стабильная версия, которой пользуются люди.
- `develop` - ветка для накопления новых функций перед выпуском.
- `feature/<short-name>` - отдельная задача или новый функционал.
- `hotfix/<short-name>` - срочное исправление для уже рабочей версии.

## Правило работы

1. Пользователи работают на версии из `main`.
2. Все новые задачи начинаются от `develop`.
3. Каждая новая задача делается в своей ветке `feature/...`.
4. Готовые задачи сначала сливаются в `develop`.
5. В `main` попадает только то, что уже проверено и готово к выпуску.

## Версии

Используем теги формата `vMAJOR.MINOR.PATCH`.

- `PATCH` - мелкие исправления без изменения сценариев работы.
  Пример: `v1.0.1`
- `MINOR` - новый функционал без поломки текущих сценариев.
  Пример: `v1.1.0`
- `MAJOR` - крупные изменения с изменением процесса работы, схемы данных или совместимости.
  Пример: `v2.0.0`

Для этого проекта безопаснее всего начинать с:

- `v1.0.0` - первая стабильная версия, которой уже пользуются.
- `v1.1.0` - следующий выпуск с новым функционалом.
- `v1.1.1` - точечное исправление после выпуска.

## Повседневная работа

### Начать новую задачу

```powershell
git checkout develop
git pull origin develop
git checkout -b feature/add-price-filter
```

### Закончить задачу

```powershell
git checkout develop
git merge feature/add-price-filter
git push origin develop
```

## Выпуск новой версии

### 1. Подготовка

Перед релизом обязательно:

1. Сделать бэкап базы:

```powershell
cd D:\codex\sm-techno-app
backup_db.bat
```

2. Проверить, что в git не попали:
- `stock_sync.db`
- `backups/`
- `transfer/`
- локальные `.env` и временные файлы

3. Проверить приложение:

```powershell
cd D:\codex\sm-techno-app\sm-techno-web
npm run lint
npm run build
```

4. Пройти ручной smoke-check по тем сценариям, которые затронули изменения:
- вход в систему;
- просмотр остатков;
- работа с заказами;
- Excel-импорт или выгрузка, если они менялись;
- интеграция с 1С, если затрагивалась бизнес-логика обмена.

### 2. Выпуск

Когда `develop` проверен:

```powershell
git checkout main
git pull origin main
git merge develop
git tag v1.1.0
git push origin main
git push origin v1.1.0
```

После этого:

- `main` становится новой рабочей версией для пользователей;
- тег фиксирует точную версию, к которой можно вернуться;
- дальнейшая разработка продолжается снова из `develop`.

## Срочное исправление рабочей версии

Если ошибка найдена уже в версии, которой пользуются люди:

```powershell
git checkout main
git pull origin main
git checkout -b hotfix/login-fix
```

После исправления:

```powershell
git checkout main
git merge hotfix/login-fix
git tag v1.1.1
git push origin main
git push origin v1.1.1
```

Потом этот же фикс нужно вернуть в `develop`:

```powershell
git checkout develop
git merge main
git push origin develop
```

## Важные правила именно для этого проекта

- Не хранить рабочую базу `stock_sync.db` в GitHub.
- Не менять схему данных, API-контракты и интеграцию с 1С без отдельного плана.
- Перед любым релизом делать бэкап базы.
- Если релиз затрагивает заказы, остатки, резервы, склады или Excel-импорт, проверка должна быть особенно внимательной.

## Минимальный практический сценарий

Если без лишней теории, рабочая схема такая:

1. `main` - то, чем пользуются люди.
2. `develop` - то, где собираем новые функции.
3. `feature/...` - отдельная задача.
4. Выпуск - это merge `develop -> main` и новый тег `vX.Y.Z`.
