# Полный цикл проверки кабинета менеджера

Статус: локальный цикл завершён, найденные дефекты исправлены. Исходная проверяемая версия: `0fa56b7`, [PR #6](https://github.com/alexdubaev/sm-techno-app/pull/6). Статус CI конкретного опубликованного коммита нужно сверять в Checks этого PR.

Предыдущий независимый просмотр был чтением кода; этот цикл добавляет воспроизводимые негативные сценарии, независимый эталон расчёта, обновление заполненной базы, проверки нагрузки, производственную сборку и расширенные браузерные сценарии. Тестовые данные синтетические, 1С и рабочая база не используются.

## Правила оценки

Для найденного дефекта фиксируются воспроизведение, ожидаемое/фактическое поведение, исправление и регрессионный тест. Успешные тесты не означают покрытия всех браузеров или рабочей 1С; фактические границы проверки будут перечислены в итогах. Отдельное разрешение на деплой этот цикл не даёт.

## Обнаружено и исправлено

1. **Чтение брало блокировку записи (существенное).** `dashboard/history/snapshots/avatar/managers` начинали `BEGIN IMMEDIATE` и синхронизировали все профили. При удержании RESERVED writer lock просмотр ждал снятия блокировки. Новый тест сначала воспроизвёл ошибку; теперь обычное чтение использует согласованную read-транзакцию, синхронизация выполняется только при новом пользователе/изменении имени. В локальном тесте чтение завершилось за ~1 мс при ещё открытом writer lock.
2. **Список снимков распаковывал все продажи (существенное).** 6 снимков по 10 000 продаж: ~834 мс и 27,5 MiB пиковых Python-аллокаций. Список теперь возвращает только метаданные; выбранный снимок загружается отдельно, по 20 продаж на страницу. На том же наборе список: ~1 мс и менее 0,1 MiB. При открытии одного снимка сервер всё ещё декодирует его JSON целиком; SQL-хранение снимков не менялось. Неизменность исторического JSON проверена отдельно.
3. **История и список сотрудников не позволяли повторить неудачную загрузку (небольшое).** Добавлены кнопки повтора; тест проверяет не только наличие кнопки, но и успешный второй запрос. Детали снимка имеют собственный retry.
4. **Ставка выше 100% доходила до серверного предпросмотра (небольшое).** Сервер уже отклонял её; теперь форма также проверяет диапазон. Десятичная запятая продолжает поддерживаться. Отрицательные значения, экспоненциальная запись и более двух знаков после запятой не принимаются.
5. **Неизвестный снимок возвращал 400 (небольшое).** Новый endpoint исправлен на 404. Проверены 401 без входа и 403 для обычных сотрудников, включая владельца кабинета.

6. **Горизонтальное переполнение WebKit на телефоне (существенное для мобильного UI).** Длинное имя выбранного сотрудника в native select увеличивало `document.scrollWidth` до 416 px при viewport 390 px, даже при корректной ширине самого поля. Проверено DOM-измерениями и отдельным минимальным воспроизведением. Поле осталось стандартным доступным select с системным выбором, но его оформление/стрелка теперь заданы CSS (`appearance: none`), текст ограничен шириной. Повтор полного сценария проходит без переполнения.

7. **Очень крупные суммы разрывались посередине числа (визуальное).** Скриншот стресс-сценария с 220 млрд ₽ показал неудобный перенос цифр в двух узких карточках. При длинной сумме мобильные карточки теперь занимают всю строку; браузерная проверка контролирует, что числовые значения остаются однострочными.

## Независимые проверки Luna 6

- Backend: 120 детерминированных случайных наборов с независимым Decimal-эталоном, перестановки и одинаковые даты, половина копейки, разные ставки, отмены и план 0; недопустимые типы, даты и лимиты; атомарный откат; конкурентное потребление одной версии; устаревший предпросмотр; закрытый месяц; смена роли/деактивация/удаление; чужое фото/кабинет/история/снимок; SVG, неподходящие байты, размеры и пиксели аватара.
- Миграция: заполненная синтетическая база создаётся **кодом предыдущего коммита `d164f3ecf1454c36f8726387de95f16fb09b57e9`**, затем открывается новым кодом. Проверяются остатки, клиентские наименования, настройки и пользователи; повторный запуск; искусственный сбой с откатом и повтором; восстановление отсутствующего индекса; четыре одновременные инициализации; повторное использование user ID не присоединяет старый архив.
- UI: запоздалые ответы при смене месяца, сотрудника и вошедшего пользователя; поиск и повтор; серверное ограничение номера страницы; сброс предпросмотра после правки; предупреждение при закрытии, Escape и переходе по ссылке; поздний ответ фото после размонтирования; ленивые снимки, пагинация и retry.

## Ограничения измерений

Показатели времени относятся к этой машине и синтетическим данным, не являются SLA. Максимальная карточка месяца (10 000 продаж) в измерении занимала ~192 мс и 7,2 MiB Python-аллокаций: расчёт всё ещё обрабатывает все продажи месяца. Нагрузочная проверка использовала 5 профилей × 10 000 продаж и 6 снимков на профиль; поведение десятков одновременно пишущих администраторов не измерялось. Реальная 1С не подключалась.

## Аудит зависимостей и исправления

Дополнительно к функциональным проверкам выполнены `npm audit` и `pip-audit` по установленным пакетам. Это проверка известных advisories на дату запуска, а не доказательство отсутствия всех уязвимостей и не эксплуатационный тест.

- Исходный `package-lock.json` совпадал с `d164f3e`. `npm audit --omit=dev` обнаружил 11 затронутых пакетов: 2 critical, 6 high, 3 moderate. Next 16.3.6 входит в уязвимые диапазоны; цепочка `proxy-addr` относится к CLI shadcn → MCP SDK → Express и отсутствует в standalone runtime. В приложении не используются `use cache`, `use server`, SVG image optimization или удалённые image patterns. Эти условия сужают применимость отдельных advisories, но не заменяют обновление.
- Обновлены Next до 16.4.3, shadcn до 4.22.1 и совместимые транзитивные зависимости без `--force`. CLI shadcn перенесён в devDependencies. Полный аудит дополнительно потребовал исправления dev-инструментов: Vitest 5.0.5 и oxfmt 0.74.0 (исправленная зависимость tinypool). После чистого `npm ci` полный `npm audit`, включая devDependencies, сообщает **0 известных уязвимостей**.
- Python-аудит старого окружения сообщил 25 записей (включая повторяющиеся записи источников) для cryptography 45.0.7 и pip 25.0.1. Для cryptography было 7 уникальных идентификаторов; код приложения использует только Fernet, а не SECT/PKCS7/проверку сертификатных цепочек. Зависимость обновлена до `cryptography>=50,<51`. Luna 6 в отдельном временном окружении проверила совместимость синтетических данных `_protect_onec_password` между 45.0.7 и 50.0.0 в обе стороны. Ключи и шифротексты после проверки удалены, в репозиторий не добавлялись. Версия 50 поддерживает Python 3.10 и имеет Windows amd64 ABI3 wheel; фактический запуск на Windows этим циклом не проверялся.
- pip — инструмент установки, не runtime-зависимость приложения. Новое тестовое окружение и CI используют pip 26.2 или новее в пределах 26.x. Серверные тесты после обновления выполняются в новом окружении, без изменения действующих секретов, алгоритма шифрования или данных 1С.

После обновления Vitest обнаружена гонка в новом тесте: он менял select до появления option. Тест теперь ждёт реального появления сотрудника, затем проверяет запоздалый ответ. Проверка не ослаблена; production-код ради этого теста не менялся.

## Воспроизведение

В чистом окружении установить `requirements-dev.txt`, выполнить `npm ci` в `sm-techno-web`, затем `npx playwright install --with-deps chromium webkit`. Python-тесты запускаются через обычный pytest с изоляцией из `tests/conftest.py`. E2E — только через npm scripts с allowlist окружения:

```sh
python -m pytest tests/auth -q --strict-markers
python -m pytest tests -q --strict-markers
# Из sm-techno-web:
npm run test:auth
npm run test:settings
node --test tests/*.test.mjs
npm run lint:ci
npx tsc --noEmit --incremental false
npm run build
npm run test:manager:e2e
npm run test:auth:e2e
npm audit
```

Тест обновления старой базы требует наличия коммита `d164f3ecf1454c36f8726387de95f16fb09b57e9`; для CI включён полный checkout истории. Production runner запускает `.next/standalone/server.js` с локальными static/public и отдельным временным backend. CI сохраняет `manager-production-browser-report` со скриншотами и отчётом, даже при успешном прогоне. Этот цикл не включает merge или deploy.
